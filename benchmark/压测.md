# 一、先定调（一句话开场）

> "我压测的目的不是拿一个 QPS 数字，而是把 Raft 本身的开销从日志、快照、打印这些干扰项里剥出来，同时验证'已确认的写入不丢'。所以我先做了隔离，再做测量，最后做故障注入。"

这句话一出，面试官就知道你不是"跑了个 benchmark"。

# 二、30 秒版

> "3 节点部署在 4 核上，用 taskset 绑核，客户端多线程各自独立 Clerk，逐操作记延迟算 P50/P99，写完再全量读回校验。单客户端写延迟稳定在 20.5ms，吞吐随并发线性涨到 166 ops/s 饱和。把 20ms 拆开发现 12.5ms 在等下一次心跳、5ms 在等 apply 轮询，实际计算不到 1ms——85% 以上是空等，不是算法慢。压测中还挖出了几个正确性 bug，比如两个客户端进程 clientId 碰撞导致静默丢写。"

# 三、2 分钟版（推荐主用，分四步讲）

## ① 工具与客户端设计

> "压测客户端是我自己写的：每个线程独立一个 Clerk，因为 Clerk 完全无锁，共享会读到撕裂的 requestId；每个线程独占一段 key 空间，避免并发写同一 key 干扰校验；前面先跑 100 次预热，让集群选完 leader，不把冷启动算进去；逐操作用 steady_clock 计时，最后排序出 P50/P90/P99/max；还有一个每 5 秒打印进度的看门狗线程——因为 Clerk 内部无限重试、RPC 无超时，集群挂了客户端会永远卡住，没有看门狗你分不清'慢'和'挂死'。"

## ② 隔离变量（这段最能体现方法）

> "默认配置测的不是 Raft：第一，Debug=true 时每 apply 一条命令就打印整个跳表，是 O(n) 输出、累计 O(n²)，必须先关；第二，maxraftstate=500 意味着快照阈值只有 50 字节，几乎每条命令触发一次全量快照，也要调。另外每轮启动前清空持久化文件，否则上一轮的状态会被继承，数字不可比。这三处不清掉，测出来的是日志系统和快照机制。"

## ③ 结果与归因

> "单线程 41 ops/s，P50 20.5ms，而且从 50 次到 500 次操作几乎不变——说明 O(n) 开销还没浮现，延迟几乎全来自固定等待。拆开是：等下一次心跳平均 12.5ms（因为 Raft::Start 追加日志后不主动触发复制，要等 25ms 周期的心跳）+ 等 applier 轮询 5ms + RPC 往返 0.5ms，实际计算不到 1ms。
>
> 加并发到 2、4 线程，吞吐 83、166，P50 几乎不动——因为多个命令被批进同一次 AppendEntries，心跳的固定成本被摊薄了。8 线程不再涨，因为 3 节点 × 8 个常驻线程 ≈ 24 个线程跑在 4 核上，已经 6 倍超配。
>
> 还做了数据量扫描：固定单线程跑 500/1500/3000 次，吞吐 42/42/41，到 3000 都没退化。因为 20ms 等待是常数，快照在当时才 64KB，O(n²) 要到十万量级才主导。"

## ④ 正确性与故障注入

> "性能之外，每次写完都全量读回校验，统计丢失和值错误——missing > 0 意味着已确认的写入丢了，这是 Raft 提交安全性被破坏，比任何 QPS 都严重。故障注入做了三种：kill follower、STOP 模拟分区、kill leader 看换主。kill follower 那轮 max 延迟 403ms、自动恢复、0 丢数据；kill leader 能看到 300–500ms 的选举尖峰。"

# 四、压测最值钱的部分：挖出了什么 bug

面试官问"压测有什么收获"时，讲这个，不要讲 QPS。挑 1–2 条，按"现象→定位→根因"讲：

## ① 静默丢写（最有故事性）

> "我用两个客户端进程先后写同一批 key，值里带不同前缀。结果第二个进程的 300 次写入全部'成功'，但读回来还是第一个进程的值——客户端收到 OK，数据却丢了。
>
> 定位到 Clerk::Uuid() 用 rand() 却从没调 srand()，所以每个进程拿到的 clientId 序列完全相同。服务端去重表 m_lastRequestId[clientId] 里已有第一个进程的进度，第二个进程的 requestId 一律小于等于它，被判为重复而跳过执行，但仍然返回 OK。
>
> 根因是跨模块契约缺陷：单看 Uuid() 正常，单看去重逻辑也正常，只有两个进程同时用才暴露。修复是用 random_device 播种并混入 pid 和单调时钟。"

## ② 持久化从未生效

> "写了个独立探针：构造 Persister、Save、析构、再构造、读。结果读回来永远是空。根因是构造函数用 trunc 模式打开落盘文件，每次启动把上次状态清零；再加上读的时候用 >> 遇到空格就停，而快照是 boost 文本归档。也就是说，整套持久化代码一行不缺，但从来没真正生效过——而 Raft 的'当选者必含所有已提交日志'恰恰依赖它。"

这两条的共同点：压测/探针才能暴露，静态读代码读不出来。这比背 Raft 论文更能证明工程能力。

# 五、必须主动说的局限（防止被追问翻车）

1. **"完成速率 ≠ 成功率"**：Clerk::Put 返回 void，内部无限重试，所以 4000 次是完成次数，无法区分"快"和"重试很多次"。要测真实成功率得先给 Clerk 加计数。
2. **单机 3 进程 + 客户端同机绑核**：测的是 CPU 和调度，不是网络；20ms 结论只在这个环境成立。
3. **不是确定性测试**：没有 6.824 tester 那种可注入延迟/分区/崩溃的模拟器，靠手工脚本。这正说明我知道正确做法。
4. **和 etcd 差 10–25 倍延迟、50–300 倍吞吐**：差距不来自 Raft 算法，来自三个实现选择——Start 不触发复制、10ms 轮询、每心跳每 peer 一个裸线程。前两条修掉能把延迟从 20ms 降到约 2ms、吞吐提升一个数量级，不需要动任何共识逻辑。

第 4 点很有杀伤力，因为它同时展示了测量、归因和改进路径。

# 六、追问速答

| 追问 | 回答 |
|---|---|
| 为什么 P50 稳定在 20.5ms？ | 因为 Start 不触发复制，均匀等心跳的一半（12.5ms）+ apply 轮询（5ms）+ RPC |
| 为什么加线程吞吐涨、延迟不涨？ | 命令被批进同一次 AppendEntries，心跳固定成本被摊薄；到 4 核饱和后不再涨 |
| 为什么吞吐不随数据量下降？ | 20ms 是常数，数据量到 3000 时快照才 64KB，O(n²) 还没成为主导 |
| 那 maxraftstate 调大是不是就好了？ | 不一定。persist 是全量重写全部日志，调大等于每命令重写更长日志；调小等于频繁全量快照。两种都是 O(N²)，没有 O(N) 的配置，只能取和最小的中间值。短跑测 Raft 用 -1 关快照隔离变量 |
| 怎么知道慢在等待而不是计算？ | 用 P50 随操作数不变 + 理论拆解对齐实测 20.5ms，并做了空心跳/加并发的对照 |
| 压测数据可信吗？ | 绑核、清状态、预热、每轮独立进程；但明确知道局限：完成速率非成功率、单机环境 |
| 如果继续优化先做什么？ | Start 后立即触发一次复制（-12.5ms）、applier 改成事件驱动（-5ms），预期 P50 到 2ms 量级 |

# 七、三个别踩的坑

1. ❌ **只报数字**："我压到了 166 QPS"——面试官会问"那和 etcd 比呢"，然后你就被动了。数字后面必须跟归因和局限。
2. ❌ **把 20ms 说成"系统性能还行"**——事实是这个实现 85% 时间在空等，要主动承认。
3. ❌ **把压测脚本说成自己的核心贡献却讲不出设计细节**——只要讲清"为什么每线程独立 Clerk、为什么预热、为什么看门狗、为什么要关 Debug"，就站得住。

# 八、收尾句

> "这套压测对我最大的价值不是数字，而是让我意识到：性能问题往往不是算法问题，而是三个实现选择和轮询模型；而正确性问题往往藏在跨模块契约里，只有把两个进程、崩溃、重启这些组合跑一遍才会暴露。"



这块我分三步做：先搭可复现的工具，再定不只看 QPS 的指标，最后用实验把瓶颈量化出来。

> **第一步，工具链。** 我写了一个一键脚本：先清掉上一轮的持久化状态，启动 3 节点集群，轮询等配置文件写全、再等选举完成；然后起多线程压测客户端，每个线程独立一个 Clerk、独占一段 key 空间；跑完做全量读回校验，最后输出吞吐和 P50/P90/P99/max 的结构化汇总。集群和客户端都用 taskset 绑在 0-3 四个核上，保证每轮环境一致。客户端还带一个 5 秒一次的看门狗——因为 Clerk 遇到错误会无限重试、RPC 又没有超时，集群挂了程序会假死，必须能区分"慢"和"挂"。
>
> **第二步，指标。** QPS 我只当"完成速率"看，因为 Clerk::Put 返回 void，调用方根本不知道是一次成功还是重试十次才成功。真正重要的是写后读回校验：所有 key 读回来，统计"丢失"和"值错误"。这个校验抓到了一个真问题：两个客户端进程的 clientId 碰撞，第二个进程的写全部被服务端去重表当成重复丢掉，但客户端收到的是 OK——静默丢写。另外做了故障注入，压测中 kill -9 一个 follower，看恢复和丢数据情况。
>
> **第三步，结果和瓶颈。** 4 核、3 节点、默认未调优配置下，1/2/4 个客户端线程的吞吐是 41 / 83 / 166 ops/s，P50 一直稳定在 20.5ms 左右，P99 约 31ms；到 8 线程吞吐不再涨、P50 升到 50ms，说明 4 核上 4 线程已经让服务端饱和。
>
> 吞吐线性涨而 P50 不动，本身就是线索：固定成本在被摊薄。我把单次 Put 的延迟拆开——Raft 的 Start 只追加日志、不主动触发复制，要等下一次 25ms 心跳，平均白等 12.5ms；提交后 applier 是 10ms 轮询一次，平均再等 5ms；本地 RPC 往返 0.5ms，真正计算不到 1ms，加起来 18ms，和实测 20.5ms 对得上。也就是 85% 以上的延迟是空等，不是计算。
>
> 批处理的证据也在同一组数里：心跳频率约 40 次/秒，如果每次心跳只带一条命令，无论多少线程吞吐都该在 40 左右；实测 4 线程到 166，正好是 40 乘 4，说明每次心跳把 4 条并发命令批量带走了。所以优化方向不是改 Raft 算法，而是 Start 后立即触发一次复制、把 apply 的轮询改成事件唤醒，预计单客户端延迟能从 20ms 降到 2ms 量级。

这段的结构是：**工具 → 指标（可信度）→ 数字 → 拆解 → 结论**。面试官最容易被打动的是"QPS 不等于成功率"和"延迟拆解能对上实测"这两点，因为它们证明你不是跑了个数字就完事。

# 二、面试官最可能追问的 10 个问题

| 追问 | 建议回答 |
|---|---|
| 为什么才 166 ops/s？etcd 是几万。 | 差距不在 Raft 算法，在三个实现选择：Start 不触发复制（-12.5ms/op）、applier 每 10ms 轮询（-5ms/op）、每心跳每 peer 新建一个 std::thread。etcd 用 WAL、事件驱动 apply 和常驻发送协程。 |
| 怎么证明瓶颈是心跳，不是 RPC 或序列化？ | 三条证据：① 延迟拆解的算术（12.5+5+0.5+<1）与实测 P50 对得上；② P50 对操作数 50/300/500 完全不敏感，说明不是 O(n) 的序列化/快照；③ 并发扫描只抬高吞吐、不改变 P50，符合"固定周期等待"的特征。 |
| P50/P90/P99 怎么算的？样本多大？ | 每个操作前后取 steady_clock，毫秒记录；各线程本地收集后汇总排序，按索引取分位；默认 2 线程×2000 次=4000 样本，预热 100 次不计入。是操作级延迟，不是系统级时间序列。 |
| 读回校验能证明什么？ | 能证明"已返回完成"的写入全部可见且值正确。不能证明"恰好一次"（重复写同值看不出来），也不能证明未完成请求的中间状态。所以它验证的是 Raft 提交安全性，不是完整的线性一致性测试。 |
| 故障注入怎么做的？ | 脚本从进程树 pgrep -P 取各节点 pid（不能用启动日志里的 pid——那是 fork 之前打印的父进程），压测开始若干秒后对目标节点 kill -9 或 kill -STOP。实测 kill follower 时 max 延迟 403ms、0 丢数据；如果杀到 leader 会看到 300–500ms 的选举尖峰。 |
| 批处理你是怎么"验证"的？ | 用吞吐反推：吞吐 ≈ 心跳频率 × 每批条数。1 线程 41≈40×1，4 线程 166≈40×4，P50 不变 → 批大小随并发增长。如果面试官追问"有没有直接测批大小"，诚实说这是反推，更严谨的做法是在 AppendEntries 里埋 entries_size 计数（这一点下面会说）。 |
| 为什么绑核？ | 单机 3 节点、每节点约 8 个常驻线程，跑在 4 核上已经 6 倍超配；不绑核调度抖动会让 P99 不可比。taskset 0-3 是固定实验预算。 |
| 为什么不用 JMeter / wrk / YCSB？ | 协议是自研 protobuf RPC + 自定义长度头，通用工具接不进来；而且我需要能直接调 Clerk、用 raft index 语义做校验的客户端。自己写约 200 行，更快也更可控。 |
| 压测工具本身可信吗？ | 它抓出过真 bug：clientId 碰撞导致静默丢写、Persister 构造即清空文件导致崩溃恢复从未生效、send(...,0) 没处理 SIGPIPE。每个修复都有前后对比复现。工具先被证明能抓 bug，再用它的数字下结论。 |
| 如果继续优化，先动哪里？ | ① Start 后立即触发一次复制；② apply 由 commit 事件唤醒替代 10ms 轮询；③ AE 发送改用固定线程池；④ 持久化从"全量重写"改追加式 WAL；⑤ 多机部署排除 loopback 影响。前两条预计单客户端 20ms→2ms、吞吐约 10 倍。 |

# 三、三处措辞要先想好，别被问穿

1. **"报告生成"** —— 目前实际产出是终端里的结构化汇总（吞吐、分位、校验结果）和 scaling_test.sh 打印的并发扫描表，没有落成文件。建议面试前花十分钟加一个输出 benchmark/reports/*.md 或 CSV 的步骤；否则口述时用"结构化汇总报告"，别让人以为有 HTML 报告。
2. **"吞吐随并发线性增长"** —— 只在 1→2→4 线程成立（41→83→166），8 线程饱和在 166、P50 反而升到 50ms。主动补这句会显得严谨；被问"为什么不继续线性"就答 4 核 CPU 饱和 + 每心跳建线程的开销。
3. **"验证批处理对吞吐的提升效果"** —— 你目前做的是从吞吐和心跳频率反推，并没有做"禁用批处理"的 A/B 对照。如果面试官抠字眼，就如实说反推逻辑；最好补一个埋点实验（下面第 4 条）。

另外两个必须诚实交代的条件：

- 所谓"3 节点"是单机 3 个进程（fork 出来），不是 3 台机器；RPC 走 loopback。
- 引用的数字是 Debug=true、maxraftstate=500 的未调优基线，这是刻意的，用来显示"等待占主导"。不要顺口说"我关了 Debug 之后测的"。

# 四、面试前建议补两个小实验（让简历完全站得住）

1. **配置对照实验（最有价值，半小时）**：把 HeartBeatTimeout 25→5ms、ApplyInterval 10→2ms，同时 Debug=false、maxraftstate=-1，重跑单线程。如果 P50 从 20.5ms 掉到 4–5ms、吞吐涨到 ~200 ops/s，就直接证明了"延迟由心跳周期锁死"，而不是靠算术推断。这个数字比任何解释都有说服力。
2. **批大小埋点（十分钟）**：在 doHeartBeat 里统计每次 AE 的 entries_size()，输出平均值。跑 1/2/4 线程，若平均批大小约为 1/2/4，就直接验证了批处理。
