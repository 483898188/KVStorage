这是一段可以直接背下来的完整项目介绍（面试开场或"讲一个你最有深度的项目"时用，时长约 1~2 分钟）：

---

> 我来讲一下我给这个 Raft 分布式 KV 项目做的压测。
>
> 这个项目的核心是从零手写 Raft 共识算法，我需要一套工具来验证它的正确性和性能，所以自己搭了一条压测工具链，分两部分：一个压测客户端和一个编排脚本。
>
> **先说工具怎么做的。** 脚本负责一键起集群、绑核、跑压测、清理。这里有几个细节：起集群前要先删掉落盘的持久化状态，保证每轮从干净状态开始，结果可比；用 taskset 把集群和客户端绑到固定的 4 个核上，排除 CPU 迁移抖动；起完集群留足冷启动时间再计时，不把选 leader 的开销算进去。
>
> 客户端这边有几个关键设计：每个线程一个独立的 Clerk 对象，因为 Clerk 没加锁，共享会读到撕裂值；每个线程独占一段 key 空间，这样并发不撞 key，读回校验能定位问题；压完之后做全量读回校验，统计丢 key 数和值错数——这个比 QPS 重要，它验证的是 Raft 的核心承诺：已确认的写入不能丢。延迟用 steady_clock 计时，输出 P50/P90/P99 分位。
>
> **再说压出了什么结论。** 4 核跑 3 节点，单线程 41 ops/s，2 线程 83，4 线程 166——吞吐随并发线性增长，但 P50 一直稳定在 20.5ms 不动。
>
> 这个"吞吐线性涨、延迟不变"的现象其实指向了瓶颈：我去读源码确认，Raft::Start 追加日志后不主动触发复制，要等每 25ms 的心跳定时器才顺带把日志发出去。所以单命令的延迟 ≈ 等下一次心跳的平均 12.5ms + 复制 + apply，正好对上 20.5ms。瓶颈是"被动等心跳"，不是网络或序列化。而吞吐线性涨，是因为并发下多个命令被批进同一次心跳的 AppendEntries，固定成本被摊薄了。
>
> **最后，这套工具最有价值的产出其实不是数字，是帮我抓出了十几个真 bug。** 比如 Clerk::Uuid 用 rand 但从不 srand，导致不同客户端进程生成相同 clientId，第二个进程的写入全被去重判成重复、静默丢写；还有 Persister 用 trunc 方式打开落盘文件，导致崩溃恢复从来没生效过。这些都是在压测和读回校验里暴露出来的。

# 第一层：压测工具怎么设计（讲 bench.cpp）

> "压测客户端是 bench，我设计了几个关键点：
> 1. 每个线程一个独立的 Clerk 对象——因为 Clerk 内部没有加锁，多个线程共享会读到撕裂状态，所以线程私有。
> 2. 每个线程独占一段 key 空间，比如线程 t 写 k_t_0 到 k_t_n，这样并发写不会撞同一个 key，读回校验的时候才能定位是哪个线程出的问题。
> 3. 把测试从日志里剥离出来——原版的 caller 每条操作都 printf，我全部去掉，否则你测的是标准输出的开销，不是 Raft。
> 4. 写完后做全量读回校验，统计两个指标：丢了多少 key、值错多少。这个比 QPS 重要，因为它直接验证 Raft 的提交安全性——已确认的写入不能丢。
> 5. 一个看门狗线程每 5 秒打印进度。因为 Clerk::Put 返回 void，失败了它内部会无限重试，集群挂了你根本看不出来是慢还是死了，看门狗用来区分这两者。
> 6. 延迟用 steady_clock 计时，输出 P50/P90/P99/max 分位。"

---

# 第二层：启动脚本怎么编排（讲 run_bench.sh）

> "脚本把整个流程自动化：起 3 节点集群、绑核、跑压测、清理。有两点比较讲究：
> 1. 起集群前必须删掉 test.conf 和持久化文件——因为修复了 Persister 之后，节点重启会真的读回上次的状态，不清理的话每轮压测会继承上一轮的数据，数据量一直涨，结果不可比。
> 2. 故障注入要用 pgrep -P 找真实的子进程 pid。因为启动器是 fork 的，而原代码在 fork 之前就调了 getpid，日志里打的 pid 永远是父进程的，三次一样，直接 grep 会打错目标。"

---

# 第三层：压测前必须调的两个配置（体现踩坑能力）

> "有两个配置不改的话，你测的根本不是 Raft，这是我实测踩出来的：
> 1. config.h 里 Debug=true 时，每 apply 一条命令就打印整个跳表，这是 O(n) 输出、累计 O(n²)，会把 Raft 开销完全淹没。必须关掉。
> 2. maxraftstate=500 时，快照阈值是 500/10 = 50 字节，而 persistData 光元信息就超过 50 字节，导致几乎每 apply 一条命令就触发一次全量快照，转储整个跳表。"

---

# 第四层：压出来的结论（这是最有面试价值的部分）

> "压测之后我得出两个比较反直觉的结论：
> 1. **延迟被心跳周期锁死。** Raft::Start 追加日志后不会主动触发复制，要等 leader 的心跳定时器（25ms 周期）才发出 AppendEntries。所以单线程吞吐稳定在 41 ops/s，P50 稳定在 20.5ms，从 50 次到 500 次操作完全不变——延迟几乎全是'等下一次心跳'。
> 2. **这个实现没有 O(N) 的配置。** persist() 每次把全部日志重新序列化重写文件，没有增量 WAL；快照每次转储整个跳表。maxraftstate 设大了，persist 每条代价线性涨；设小了，快照极频繁。不管怎么调都是二次方，中间某个值只是最小化两者的和。这是这个实现的设计属性，工业实现用追加式 WAL + 定期 compaction 来避免。"

---

# 第五层：压测帮我抓到的一批真 bug（亮点，一定要讲一两个）

> "这套工具最有价值的产出不是数字，而是帮我抓到了十几个真 bug，我举两个最典型的：
> 1. Clerk::Uuid() 用了 rand() 但从不 srand()，导致不同客户端进程生成完全相同的 clientId，第二个进程的写入全被去重表判成重复而不执行，却返回 OK——静默丢写。这是我写 dedup_test 专门复现出来的。
> 2. Persister 构造函数用 trunc 方式打开落盘文件，每次启动都把上次状态抹掉，意味着崩溃恢复从来没真正生效过，持久化的语义是架空的。还叠加了 ifs >> str 遇空白截断、写入后不 flush 几个问题。
> 3. 还有一个印象深的：MprpcChannel 用 send(fd, ..., 0) 发数据，对端一挂内核就发 SIGPIPE，把本进程直接打死，后面的重连重发逻辑根本执行不到。故障注入实测时表现为 exit code 141。"

# 面试官可能追问 + 你的应答

## Q：为什么要读回校验，而不是只看 QPS？

> "因为 Raft 的核心承诺是'已确认写入不丢、状态机一致'。如果为了性能牺牲了正确性，QPS 再高也没意义。而且 Put 返回 void，失败不可见，QPS 是完成速率不是成功率，读回校验能兜住这一点。"

## Q：你的 QPS 很低啊，才 41？

> "对，但低是有原因的，而且这正是我想展示的——它暴露了实现的问题：心跳驱动复制，而不是命令驱动。工业 Raft 是收到新命令就立刻发一轮 AppendEntries，或者批量流水线。我这里延迟直接等于心跳周期。如果面试官问怎么优化，我会说让 Start 主动触发复制，以及做批处理。"

## Q：怎么保证压测结果可比？

> "每轮清空持久化状态、固定绑核、预热先让集群选完 leader 再计时、用 steady_clock 避开系统时间回拨。"

## 简历第①条："一键式压测工具链"

**面试官问：你这个工具链是怎么搭的？**

## 简历第②条："166 ops/s / P50 稳定 20.5ms"

**面试官问：这个数字怎么来的？吞吐为什么是线性增长？**

> "4 核跑 3 节点，单线程是 41 ops/s，2 线程 83，4 线程 166——吞吐随并发线程数线性增长，但 P50 一直稳定在 20.5ms 不动。
>
> 这个'线性增长 + 延迟不变'的组合很有意思，它说明的是：多个客户端命令在同一轮心跳里被批进同一次 AppendEntries，固定成本（一次心跳 + 一次复制 + 一次 apply）被摊薄到多个命令上。所以并发越高，单次心跳携带的命令越多，吞吐越高，而每个命令的延迟没变。
>
> 这是这个项目里唯一'看起来合理'的伸缩行为。"

---

## 简历第③条："定位延迟瓶颈为 Start 后被动等待心跳"

**面试官问：你怎么定位到这个瓶颈的？**

> "看数据 + 读源码两条腿。数据上，单线程 41 ops/s 对应延迟约 24ms，而且从 50 次到 500 次操作 P50 完全不变——如果是 O(n) 的开销，延迟会随数据量涨，它不涨，说明延迟是个常数，我怀疑是某个固定周期。
>
> 然后读源码确认：Raft::Start 追加日志到本地后不主动触发复制，而是等 leaderHearBeatTicker 每 25ms 的心跳才顺带把日志发出去。所以一个命令的延迟 ≈ 等待下一次心跳的平均时间（12.5ms）+ 复制 + apply，加起来正好对上 20.5ms 的 P50。瓶颈就是'被动等心跳'，而不是网络或序列化。"

# ⚠️ 一个必须提醒你的点（避免穿帮）

你简历写的是"验证批处理对吞吐的提升效果"。但从代码和 README 看，这个项目并没有实现显式的命令批处理——批处理效果是通过多线程并发自然形成的（多个命令恰好落进同一次心跳的 AppendEntries），不是你改了 Raft 的复制逻辑去主动攒批。

所以面试官如果追问"你具体怎么做批处理的？改了哪些代码？"，你要诚实：

> "批处理不是我主动改出来的，是并发场景下自然观察到的——多个线程的命令恰好被同一次心跳的 AppendEntries 捎带出去。我当时是通过跑 1/2/4 线程观察吞吐线性增长来验证这个批化效果的。如果要做显式优化，方向是让 Start 收到命令就主动触发一轮复制，而不是等心跳。"

简历上那句话如果措辞太满（"验证批处理...提升效果"）其实还能圆过去，但千万别夸大成"我实现了批处理"。"验证了...效果" = 观察到并证明了，这个定位是安全的，照着上面答就行。
