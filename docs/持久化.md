● 一、要持久的其实是两样东西，分别由两个层负责

  ┌───────────┬────────────────────────────────────────────────────────────────┬──────────┬─────────────────────────┐
  │           │                              内容                              │  负责方  │          文件           │
  ├───────────┼────────────────────────────────────────────────────────────────┼──────────┼─────────────────────────┤
  │ raftstate │ currentTerm、votedFor、lastSnapshotIncludeIndex/Term、全部日志 │ Raft     │ raftstatePersist<i>.txt │
  ├───────────┼────────────────────────────────────────────────────────────────┼──────────┼─────────────────────────┤
  │ snapshot  │ SkipList 全量数据 + m_lastRequestId 去重表                     │ KvServer │ snapshotPersist<i>.txt  │
  └───────────┴────────────────────────────────────────────────────────────────┴──────────┴─────────────────────────┘

  文件名按节点号区分（Persister.cpp 构造函数），两个文件都在当前工作目录下——和 test.conf 一样有 cwd 依赖，重启必须从同一目录启动。

  两份文件被一个 shared_ptr<Persister> 共享（前面说的"线 3"），Raft 和 KvServer 各写自己的那一份：

  // Raft::persist()        → 只写 raftstate，高频路径
  m_persister->SaveRaftState(data);
  // Raft::Snapshot() / InstallSnapshot() → 两份一起写
  m_persister->Save(persistData(), snapshot);

  这个拆分是有意的：正常运行时每接受一轮 AE 都要 persist()，只重写 raftstate、不碰快照文件。

  二、什么时候落盘

  persist() 的调用点覆盖了论文 Figure 2 的全部要求：

  ┌─────────────────────────────────────┬───────────────────────────────────────────────────┬──────────────┐
  │                位置                 │                     触发原因                      │ 是否论文要求 │
  ├─────────────────────────────────────┼───────────────────────────────────────────────────┼──────────────┤
  │ doElection                          │ currentTerm++ / m_votedFor = me 之后、发 RPC 之前 │ ✅  必须      │
  ├─────────────────────────────────────┼───────────────────────────────────────────────────┼──────────────┤
  │ RequestVote                         │ DEFER { persist(); } 包住整个函数                 │ ✅  必须      │
  ├─────────────────────────────────────┼───────────────────────────────────────────────────┼──────────────┤
  │ AppendEntries1                      │ DEFER { persist(); }，任何一次接受 AE             │ ✅  必须      │
  ├─────────────────────────────────────┼───────────────────────────────────────────────────┼──────────────┤
  │ InstallSnapshot                     │ 更新 term / 安装快照后                            │ ✅  必须      │
  ├─────────────────────────────────────┼───────────────────────────────────────────────────┼──────────────┤
  │ Snapshot                            │ 截断日志后                                        │ ✅  必须      │
  ├─────────────────────────────────────┼───────────────────────────────────────────────────┼──────────────┤
  │ sendRequestVote / sendAppendEntries │ 发现对方 term 更高、自己退位时                    │ ✅  必须      │
  └─────────────────────────────────────┴───────────────────────────────────────────────────┴──────────────┘

  两个细节值得单独看：

  doElection 里 persist 的顺序是"先改状态、后落盘、再发 RPC"：

  m_status = Candidate;
  m_currentTerm += 1;
  m_votedFor = m_me;
  persist();                    // ★ 在发 RequestVote 之前
  ...
  std::thread t(&Raft::sendRequestVote, ...); t.detach();

  顺序反了就会出现"已经对外承诺了投票，但崩溃重启后忘了"——同一任期投两票。

  persist() 全程持有 m_mtx。doElection 是 lock_guard 包的，RequestVote/AppendEntries1 用 DEFER
  在锁作用域内落盘（注释特意写"由于这个局部变量创建在锁之后，因此执行persist的时候应该也是拿到锁的"）。安全性没问题，但意味着每次心跳/每次应用都要在锁内做一次 boost 序列化 + 文件写
  + flush，这是这个实现最主要的性能瓶颈，代码里也留了 todo。

  三、序列化格式：三层嵌套

  这是本项目持久化最需要画图的地方。以一次 Snapshot 为例：

  snapshotPersist<i>.txt  ← boost text_oarchive(KvServer)
                               ├── m_serializedKVData = SkipList.dump_file()
                               │       └── boost text_oarchive(SkipListDump<K,V>)
                               │               └── Level 级链表上的每个 key/value
                               └── m_lastRequestId  (clientId -> requestId)

  raftstatePersist<i>.txt ← boost text_oarchive(BoostPersistRaftNode)
                               ├── m_currentTerm / m_votedFor
                               ├── m_lastSnapshotIncludeIndex / Term
                               └── m_logs : vector<string>
                                       └── 每条 = LogEntry::SerializeAsString()   ← protobuf 嵌在 boost 里

  三层三种格式：最外层 boost 文本归档 → 中间是 protobuf（LogEntry）或 boost（SkipListDump）→ 最内层才是业务数据。BoostPersistRaftNode 里那个 std::vector<std::string> m_logs        
  就是刻意的"boost 里套 protobuf"，为了不让 boost 去序列化 protobuf 的生成类。

  readPersist 是严格镜像：

  if (data.empty()) return;                       // 首次启动，无状态
  boost::archive::text_iarchive ia(iss); ia >> boostPersistRaftNode;
  m_currentTerm = ...; m_votedFor = ...;
  m_lastSnapshotIncludeIndex/Term = ...;
  m_logs.clear();
  for (auto& item : boostPersistRaftNode.m_logs) {
      raftRpcProctoc::LogEntry logEntry;
      logEntry.ParseFromString(item);             // 逐条反序列化回去
      m_logs.emplace_back(logEntry);
  }

  注意没有持久化 firstIndex——它由 m_lastSnapshotIncludeIndex + 1 推出，所以只要快照点存对了，日志偏移就自动对上。

  四、Persister 的写入策略

  void Persister::SaveRaftState(const std::string& data) {
    std::lock_guard<std::mutex> lg(m_mtx);
    clearRaftState();                    // 关闭流 → trunc 重开（清空文件 + size 归零）
    m_raftStateOutStream << data;
    m_raftStateOutStream.flush();        // ★ 必须
    m_raftStateSize += data.size();
  }

  三个设计点：

  1. 流常开 + 显式 trunc。写流以 app 模式打开常驻（Persister::Persister），需要覆盖时才 clearRaftState() 关掉、以 trunc 重开。不用每次 open/close。
  2. m_raftStateSize 内存缓存。GetRaftStateSize() 直接返回这个数，不做 stat——因为它被 IfNeedToSendSnapShotCommand 高频查询。
  3. flush() 但不用 fsync。注释写得很坦诚：flush 只能保证数据离开用户态缓冲区，扛不住断电/宕机，但为了避免每次 persist 都陷入内核，本项目从简。

  五、崩溃恢复的完整流程

  重启一个节点，恢复发生在两个阶段、由两个层各做一半：

  阶段 1：Raft::init（raft.cpp:994）

  m_currentTerm = 0; m_status = Follower; m_commitIndex = 0; m_lastApplied = 0; m_logs.clear();
  m_votedFor = -1;
  m_lastSnapshotIncludeIndex = 0; m_lastSnapshotIncludeTerm = 0;
  m_lastResetElectionTime = now(); m_lastResetHearBeatTime = now();

  readPersist(m_persister->ReadRaftState());      // ★ 覆盖上面的初值
  if (m_lastSnapshotIncludeIndex > 0) {
      m_lastApplied = m_lastSnapshotIncludeIndex;  // 快照覆盖的部分不用再 apply
  }

  关键：m_commitIndex 故意不恢复（保持 0）。这是合法的——commitIndex 是易失状态，恢复后作为普通 follower 靠新 leader 的 leaderCommit 重新推进。日志本身是持久的，commit 位置不是。   

  阶段 2：KvServer 构造函数末尾（kvServer.cpp:437-440）

  auto snapshot = persister->ReadSnapshot();
  if (!snapshot.empty()) {
      ReadSnapShotToInstall(snapshot);
  }

  ReadSnapShotToInstall → parseFromString(snapshot) → m_skipList.load_file(m_serializedKVData)
                        → 顺带恢复 m_lastRequestId

  注意 KvServer::ReadSnapShotToInstall 没有更新 m_lastSnapShotRaftLogIndex——只有走 GetSnapShotFromRaft（从网络装快照）那条路才会更新它。构造函数里那个值是显式初始化为 0
  的（kvServer.cpp:436），而 Raft::init 已经把 m_lastApplied 提到了快照点，所以重启后 raft
  只会推送快照点之后的条目，不会重复推旧的。这条链是自洽的，但依赖两个层各自记住半边状态，比较脆弱。

  之后的恢复就是普通的 follower 行为：参与选举、接受 AE、applierTicker 把 [snapshotIdx+1, commitIndex] 的条目重新推给 KvServer。重放是安全的，因为 GetCommandFromRaft 有两道闸门：  

  if (message.CommandIndex <= m_lastSnapShotRaftLogIndex) return;   // 快照已覆盖
  if (!ifRequestDuplicate(op.ClientId, op.RequestId)) { ...执行... } // 去重表已随快照恢复

  六、Persister 里已经修掉的四个真实 bug

  这个文件的注释是一份不错的"崩溃恢复踩坑实录"，四个 bug 都是让崩溃恢复整体失效级别的：

  ┌────────────────────────────────┬───────────────────────┬──────────────────────────────────────────────────────────────────────────────────┬──────────────────────────┐
  │              Bug               │        原实现         │                                       后果                                       │          现实现          │
  ├────────────────────────────────┼───────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────────┤
  │ 构造函数用 trunc 打开文件      │ ios::out | ios::trunc │ 每次进程启动都把上次落盘的状态抹掉，ReadSnapshot() 必然读到空 → 崩溃恢复从未生效 │ app 模式，不存在则创建   │
  ├────────────────────────────────┼───────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────────┤
  │ ReadSnapshot 重开流用默认 mode │ open(name) = ios::out │ 对已存在文件会截断 → 每读一次快照就清零                                          │ 显式 ios::out | ios::app │
  ├────────────────────────────────┼───────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────────┤
  │ 读文件用 ifs >> str            │ operator>> 遇空白即停 │ 快照是 boost 文本归档、全是空格换行 → 只读到第一个词                             │ ss << ifs.rdbuf() 整体读 │
  ├────────────────────────────────┼───────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────────┤
  │ 写完不 flush                   │ 数据停在用户态缓冲    │ 被 SIGKILL 直接丢，违反"先落盘再回复"语义                                        │ 每次写后 flush()         │
  └────────────────────────────────┴───────────────────────┴──────────────────────────────────────────────────────────────────────────────────┴──────────────────────────┘

  前两个叠加的效果是"持久化代码看起来齐全，但恢复路径永远拿到空"，而且不会报错——是最难发现的那类 bug。注释里提到 benchmark/_persist_probe.sh
  实测证明了这点，说明是靠探针才发现的，不是靠读代码。

  七、仍然存在的问题

  1. Save() 不是原子的，而且是"先清空再写"

  void Persister::Save(raftstate, snapshot) {
    clearRaftStateAndSnapshot();          // 两个文件都被 trunc
    m_raftStateOutStream << raftstate;
    m_snapshotOutStream << snapshot;
    flush(); flush();
  }

  在这个窗口内崩溃（或进程被 kill），两个文件都是空的——所有状态一次性丢失。而且这和"两个文件必须互相匹配"的要求是冲突的：raftstate 里的 lastSnapshotIncludeIndex 要和 snapshot      
  里的内容对应，一个有一没有就是不一致状态。工业实现的标准做法是写临时文件 + fsync + rename（rename 在同一文件系统上是原子的），这里完全没做。

  2. 没有 fsync。flush() 只到 page cache，机器掉电/内核 panic 仍会丢。这个项目是学习实现，可以接受，但要知道它和"持久化"的语义有差距。

  3. persist() 在 Raft 的锁内做文件 IO。每一次 AE、每一次心跳回复都要序列化整个日志并写盘，全程持
  m_mtx——心跳处理、选举计时全被阻塞。日志越长越慢，而唯一的缓解手段（快照）本身也要走这条锁内的 Save()。

  4. Save() 之后 m_raftStateSize 归零。clearRaftState() 会把 size 置 0，但 Save() 里没有再累加回去。于是刚做完快照的一瞬间 GetRaftStateSize() == 0，IfNeedToSendSnapShotCommand     
  的阈值判断暂时失效。影响很小（下一次 AppendEntries1 的 persist() 会立刻修正），但属于"两处维护同一份状态却没同步"的典型疏漏。

  5. m_commitIndex 与 m_lastApplied 都不持久化。这是论文允许的（Figure 2 明确标注 volatile），但代价是重启后已经 apply 过的条目会被完整重放一遍。正确性完全压在 KvServer
  的去重逻辑上：m_lastRequestId 必须随快照恢复（它是），m_lastSnapShotRaftLogIndex 必须初始化正确（构造函数里是 0，靠 Raft::init 那边把 m_lastApplied 提到快照点来兜）。

  6. 恢复期的两个大小写不一致的小坑：KvServer 构造函数读快照走的是 ReadSnapShotToInstall（不更新 m_lastSnapShotRaftLogIndex），而网络装快照走
  GetSnapShotFromRaft（更新）。两条路都写同一个状态机，但只有一条更新那个游标。

  ---

  总结：持久化的内容划分（raftstate 归 Raft、snapshot 归 KvServer、一个 Persister 共享）和调用时机都符合论文要求；readPersist → Raft::init → KvServer
  读快照这条恢复链也是自洽的。真正的软肋在文件层的原子性和耐久性——"先 trunc 再写两个文件"在崩溃窗口内会全丢，且没有 fsync/原子 rename。而从 Persister.cpp
  里那四段注释看，这个项目历史上最严重的问题不是设计，而是恢复路径从来没被跑通过（启动时自毁状态 + 读快照时清零），修掉之后才谈得上"崩溃恢复"这四个字。
