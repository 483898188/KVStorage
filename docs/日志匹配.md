# 日志匹配：两套下标、三种回退与一处与论文的偏差

> 项目：自研 Raft 共识 + 分布式 KV（`KVstorageBaseRaft-cpp`）
> 相关代码：`src/raftCore/raft.cpp`、`src/raftCore/include/raft.h`
> 相关文档：[leader选举](./leader选举.md)、[持久化](./持久化.md)、[系统设计总览](./系统设计总览.md)

## 0. 先说清楚：难在「两套下标」

`m_logs` 是 `std::vector<LogEntry>`，但 Raft 语义里的 `logIndex` **从 1 开始**，而且会被快照从头部裁掉。于是同一个日志条目有两个坐标：

| 坐标 | 含义 | 起点 |
|---|---|---|
| **logIndex** | Raft 逻辑下标，出现在 `LogEntry.logindex()`、`prevLogIndex`、`commitIndex`、`ApplyMsg.CommandIndex` | 1（快照后从 `snapshotIdx+1` 起） |
| **sliceIndex** | `std::vector` 物理下标 | 0 |

桥接函数只有一个（`raft.cpp`）：

```cpp
int Raft::getSlicesIndexFromLogIndex(int logIndex) {
  myAssert(logIndex > m_lastSnapshotIncludeIndex, ...);   // 严格大于
  myAssert(logIndex <= lastLogIndex, ...);
  return logIndex - m_lastSnapshotIncludeIndex - 1;       // ← 唯一的换算
}
```

这个 `- m_lastSnapshotIncludeIndex - 1` 是理解本项目日志匹配的钥匙。后面所有看起来别扭的写法，几乎都是为了绕开快照造成的偏移。

---

## 一、把快照点当成一条「虚拟日志」

这是本实现里最漂亮的一处设计。`getLogTermFromLogIndex` 对快照边界做了特判：

```cpp
int Raft::getLogTermFromLogIndex(int logIndex) {
  myAssert(logIndex >= m_lastSnapshotIncludeIndex, ...);   // 这里允许"等于"
  myAssert(logIndex <= lastLogIndex, ...);
  if (logIndex == m_lastSnapshotIncludeIndex) return m_lastSnapshotIncludeTerm;  // ★ 虚拟条目
  else return m_logs[getSlicesIndexFromLogIndex(logIndex)].logterm();
}
```

注意两个函数断言的不等号方向是**刻意不同的**：

- `getSlicesIndexFromLogIndex` 要求 `> snapshotIdx`（vector 里确实没有这一条）；
- `getLogTermFromLogIndex` 允许 `>=`（快照点用 `m_lastSnapshotIncludeTerm` 顶替）。

于是一条快照覆盖的日志在匹配检查里**和真实条目一样可比较**：

```cpp
bool Raft::matchLog(int logIndex, int logTerm) {
  myAssert(logIndex >= m_lastSnapshotIncludeIndex && logIndex <= getLastLogIndex(), ...);
  return logTerm == getLogTermFromLogIndex(logIndex);
}
```

`matchLog` 有多简单，就说明这个抽象有多成功——它把「日志可能在 vector 里、也可能在快照里」这件事完全藏在了 `getLogTermFromLogIndex` 后面。

## 二、leader 侧：`nextIndex` / `matchIndex` 的维护

### 构造 `prevLogIndex` / `prevLogTerm`

```cpp
void Raft::getPrevLogInfo(int server, int* preIndex, int* preTerm) {
  if (m_nextIndex[server] == m_lastSnapshotIncludeIndex + 1) {   // 要发的是第一条真实日志
    *preIndex = m_lastSnapshotIncludeIndex;
    *preTerm  = m_lastSnapshotIncludeTerm;                        // ← 于是 prev 落在快照点上
    return;
  }
  *preIndex = m_nextIndex[server] - 1;
  *preTerm  = m_logs[getSlicesIndexFromLogIndex(*preIndex)].logterm();
}
```

那个 `if` 分支**不是优化，是必需**——`nextIndex-1 == snapshotIdx` 时调 `getSlicesIndexFromLogIndex` 会撞断言（它要求严格大于）。同一个偏移问题，又一次泄漏到调用点。

### 构造 `entries`

`doHeartBeat` 里有完全对称的第二处特判：

```cpp
if (preLogIndex != m_lastSnapshotIncludeIndex) {
    for (int j = getSlicesIndexFromLogIndex(preLogIndex) + 1; j < m_logs.size(); ++j)
        *appendEntriesArgs->add_entries() = m_logs[j];
} else {
    for (const auto& item : m_logs)                      // 从 vector 头开始
        *appendEntriesArgs->add_entries() = item;
}
```

策略是**「发到底」**：从 `prevLogIndex+1` 一直发到 leader 的 `lastLogIndex`，而不是只发一个。这让 follower 一次就能追上，代价是冲突时浪费带宽。代码里还用断言把这个不变量钉住了：

```cpp
myAssert(args->prevlogindex() + args->entries_size() == lastLogIndex, ...);
```

### 回复处理

对 `matchIndex` 用了 `max`——这是个考虑了幂等性的细节：

```cpp
m_matchIndex[server] = std::max(m_matchIndex[server], args->prevlogindex() + args->entries_size());
m_nextIndex[server]  = m_matchIndex[server] + 1;
```

注释写明了原因：心跳会**重复**发送同一批日志，如果直接赋值，一个条目会让 `matchIndex` 涨 N 次。而 `nextIndex` 可以直接赋值（它是 `matchIndex+1` 的从属量）。

失败时：

```cpp
if (!reply->success()) {
    if (reply->updatenextindex() != -100)     // -100 是"你任期太旧"的哨兵值
        m_nextIndex[server] = reply->updatenextindex();   // 注意：不更新 matchIndex
}
```

## 三、follower 侧：三道校验，三种回退值

`AppendEntries1` 收到请求后的判定顺序（`raft.cpp`）：

```cpp
// ① 任期
if (args->term() < m_currentTerm) { success=false; updatenextindex = -100; return; }
if (args->term() > m_currentTerm) { 三变(状态/term/votedFor); }
m_status = Follower;                       // 同 term 的 candidate 见到 leader 也要退位
m_lastResetElectionTime = now();           // 心跳续命

// ② prevLogIndex 越界
if (args->prevlogindex() > getLastLogIndex()) {
    success=false; updatenextindex = getLastLogIndex() + 1;    // 我太短
    return;
} else if (args->prevlogindex() < m_lastSnapshotIncludeIndex) {
    success=false; updatenextindex = m_lastSnapshotIncludeIndex + 1;   // 我太快（在快照里）
    return;                                                             // ★ 必须 return
}

// ③ prevLogTerm 是否匹配
if (matchLog(args->prevlogindex(), args->prevlogterm())) {
    ...写入...
} else {
    // 回扫：找到与 prevLogTerm 不同的那个位置，让 leader 一步跳过去
    reply->set_updatenextindex(args->prevlogindex());
    for (int index = args->prevlogindex(); index >= m_lastSnapshotIncludeIndex; --index) {
        if (getLogTermFromLogIndex(index) != getLogTermFromLogIndex(args->prevlogindex())) {
            reply->set_updatenextindex(index + 1);
            break;
        }
    }
}
```

回退值**不是简单的 `-1`**，而是由 follower 精确计算（论文 §5.3 的优化）——这是本项目比 6.824 基础实现多出的一层。不过代码注释自己承认效果有限：

```cpp
// 很多都是优化了0，因为多数冲突只涉及单个 term，回扫立刻停在原地
```

### 那颗必须 `return` 的地雷

②的第二个分支里那句 `return` 是有血泪的，注释写得很清楚：

> 不 `return` 会落进 `matchLog()`，而 `matchLog` 的第一行断言要求
> `logIndex >= m_lastSnapshotIncludeIndex`——这里恰好违反，`myAssert`
> 又是 `std::exit(EXIT_FAILURE)`，节点进程直接死。

而触发条件是「follower 的快照比 leader 以为的更新」，属于**完全正常的落后/恢复路径**。这是日志匹配里最危险的一颗地雷。

## 四、写入阶段：覆盖式，不是截断式（与论文的实质偏差）

论文伪码写得很直接：

> If an existing entry conflicts with a new one (same index but different terms),
> delete the existing entry and **all that follow it**.

本项目没这么做（`AppendEntries1`）：

```cpp
for (int i = 0; i < args->entries_size(); i++) {
    auto log = args->entries(i);
    if (log.logindex() > getLastLogIndex()) {
        m_logs.push_back(log);                     // 追加
    } else {
        if (m_logs[getSlicesIndexFromLogIndex(log.logindex())].logterm() == log.logterm() &&
            m_logs[getSlicesIndexFromLogIndex(log.logindex())].command() != log.command()) {
            // 违反 Log Matching，直接 exit
            myAssert(false, "两节点 logIndex 和 term 相同，但 command 却不同！！");
        }
        if (m_logs[getSlicesIndexFromLogIndex(log.logindex())].logterm() != log.logterm())
            m_logs[getSlicesIndexFromLogIndex(log.logindex())] = log;   // 就地覆盖
    }
}
```

它**只覆盖冲突位置，从不截断尾部**。注释解释了动机：

> 不能直接截断，必须一个一个检查，因为发送来的 log 可能是之前的，
> 直接截断可能导致「取回」已经在 follower 日志中的条目。

这个顾虑是对的（延迟的过期 AE 确实会造成破坏），但解法带来的后果是：

**当 follower 的日志比 leader 长，且多出来的尾部来自旧任期时，它们永远不会被删除。**

论文明确要求删除，目的是维持 Log Matching Property 的推论——
*如果两个日志在某个 index 上 term 相同，则之前的所有条目都相同*。
保留尾部意味着 follower 的日志不再是 leader 日志的前缀。

两件事缓解了它的实际危害：

1. `entries` 总是从 `prevLogIndex+1` 发到 leader 末尾，所以**正常的窗口内**所有位置都会被覆盖成 leader 的版本，等价于截断；
2. `sendAppendEntries` 里只允许**当前 term 的条目**带动 `commitIndex`，这挡住了旧 term 条目的「复活」路径。

但残留风险是真实的：这个 follower 的 `lastLogIndex` 会偏高，而 `UpToDate` 又是拿「最后一条的 `(term, index)`」比大小的——**一个带着旧任期多余尾部的节点，在选举中可能显得比实际更「新」**。这类问题很难靠读代码断言，属于值得专门写个分区测试去压的地方。

另外，那个 `myAssert(false, "logIndex 和 term 相同但 command 不同")` 是**唯一一处主动检查 Log Matching 不变量**的地方，检查对象还是「同位置同 term 但内容不同」这种理论上不可能出现的情况。它一旦触发同样是 `exit`，而不是把节点踢出集群。

## 五、commit 推进：两个保护都在

```cpp
if (*appendNums >= 1 + m_peers.size() / 2) {            // 保护一：多数派
    *appendNums = 0;
    if (args->entries_size() > 0 &&
        args->entries(args->entries_size() - 1).logterm() == m_currentTerm) {
        // 保护二
        m_commitIndex = std::max(m_commitIndex, args->prevlogindex() + args->entries_size());
    }
}
```

**保护二就是论文 §5.4.2 那个著名的坑**：「leader 只能通过提交自己当前 term 的日志来间接提交之前 term 的日志」。很多人漏掉它，会导致已提交条目被覆盖。这里不仅实现了，注释还完整写明了推理：

> 只有当前 term 有 log 成功提交，之前 term 的 log 才可以被提交。

follower 侧则保守取小：

```cpp
if (args->leadercommit() > m_commitIndex)
    m_commitIndex = std::min(args->leadercommit(), getLastLogIndex());
```

## 六、持久化：靠偏移量重建

`persistData` 存的是 `m_currentTerm`、`m_votedFor`、`m_lastSnapshotIncludeIndex/Term` 和 `m_logs`（每条 `LogEntry::SerializeAsString()`），**不存 `firstIndex`**——因为它可以由 `lastSnapshotIncludeIndex + 1` 推出。恢复时 `readPersist` 把 `lastSnapshotIncludeIndex/Term` 一并还原，偏移就重新对上了。

## 七、隐患清单

按危险程度排：

1. **`myAssert` 一律 `std::exit(EXIT_FAILURE)`**（`src/common/util.cpp:5`）。
   日志匹配路径上 `matchLog`、`getSlicesIndexFromLogIndex`、`getLogTermFromLogIndex`
   **全部带断言**，而这些函数被调用得极其频繁。一次越界 = 整个节点进程退出，没有降级、没有日志上报。
   第②分支那个 `return` 就是在补这个洞（补在调用点而非断言处，属于哪里漏了补哪里）。
2. **不截断尾部**（见第四节）。与论文偏差，有残留风险。
3. **`matchIndex[m_me]` 恒为 0**。leader 自己的进展靠 `appendNums` 初值 1 兜着，
   所以提交逻辑没错；但一旦要加 ReadIndex / 租约读（都依赖「leader 自己已匹配到
   `lastLogIndex`」），这里会立刻踩坑。
4. **`m_nextIndex` / `m_matchIndex` 的注释有误导**。`raft.h:48-49` 写「有效下标1开始」，
   但实际 vector 是 `0..size-1` 全用，下标就是 server id。「从 1 开始」说的是**值是 logIndex，
   从 1 开始**（`nextIndex[me] = lastLogIndex + 1`），注释表述容易让人写成 `m_nextIndex[i+1]`。
5. **回扫优化收益有限**（注释自认「很多都是优化了0」），但至少方向对。

---

## 总结

日志匹配的核心机制（`prevLogIndex`/`prevLogTerm` 检查、Log Matching Property、
多数派 + 当前任期双重 commit 保护）都实现对了，而且比基础版多了 follower
精确计算回退位置这一层优化。

复杂度几乎全部来自**快照偏移**——两套下标、两个特判分支、三处断言，
以及那个必须 `return` 否则进程退出的地雷。
真正与论文有实质分歧的只有一处：**写入时覆盖而不截断尾部**。
