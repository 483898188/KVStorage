# 案例 A：杀一个节点，把客户端也打死了

## A.0 一句话版本

**向一个已被对端关闭的 TCP socket 写数据，内核会发 `SIGPIPE`，而它的默认动作是终止进程。**
`MprpcChannel` 发请求时用的是 `send(fd, buf, len, 0)`，于是集群里任何一个节点挂掉，
**正在向它发请求的进程会直接被信号打死**——连它下面那段"失败就重连重发"的逻辑都来不及跑。

## A.1 发现：故障注入一跑就挂

第一篇案例修完之后，我的压测工具已经能跑通了。接下来做的是**故障注入**——在压测进行中杀掉一个节点：

```bash
FAULT=kill FAULT_NODE=1 ./benchmark/run_bench.sh
```

行为是：压测开始 N 秒后，后台对某个节点执行 `kill -9`。

第一次跑，结果很干脆：

```
[bench] 节点 pid: 315552 315558 315584
[bench] >>> 注入故障：kill -9 node1 (pid 315558)
[bench] 压测结束 (exit=141)
```

**`exit=141`。**

`141 = 128 + 13`，而信号 13 就是 **`SIGPIPE`**。也就是说：**压测进程不是"测出问题"，而是被信号打死了。**

而它本该输出的结果、延迟分位、读回校验——全都没有。

## A.2 定位

`SIGPIPE` 的来源很明确：向一个**对端已经关闭**（或已 RST）的 socket 写数据时，内核会先发 `SIGPIPE` 给写入方，再让 `write/send` 返回 `-1/EPIPE`。

我们杀掉 node1，它上面所有已建立的 TCP 连接被内核关闭。而压测客户端（以及另外两个 Raft 节点）手里还攥着到 node1 的连接。

看客户端的发送代码（`src/rpc/mprpcchannel.cpp`）：

```cpp
// 发送rpc请求
// 失败会重试连接再发送，重试连接失败会直接return
while (-1 == send(m_clientFd, send_rpc_str.c_str(), send_rpc_str.size(), 0)) {
  char errtxt[512] = {0};
  sprintf(errtxt, "send error! errno:%d", errno);
  std::cout << "尝试重新连接，对方ip：" << m_ip << " 对方端口" << m_port << std::endl;
  close(m_clientFd);
  m_clientFd = -1;
  std::string errMsg;
  bool rt = newConnect(m_ip.c_str(), m_port, &errMsg);
  if (!rt) { controller->SetFailed(errMsg); return; }
}
```

**注意这里有个很讽刺的地方**：这段代码的意图是"send 失败就重连、重发"，逻辑本身是对的。但 `flags` 传的是 `0`，所以内核先在 `send` 返回之前就把进程杀了——**这段重连逻辑从来没被执行过。**

## A.3 修复

```cpp
// 必须带 MSG_NOSIGNAL：向已被对端关闭的 socket 写数据时，内核默认会发 SIGPIPE，
// 而 SIGPIPE 的默认动作是【终止进程】。原实现用的是 flags=0，结果是对端一挂，
// 本端进程直接被信号打死，下面这段"重连后重发"的逻辑根本来不及执行。
// 带上 MSG_NOSIGNAL 后，send 返回 -1/EPIPE，重连逻辑才真正生效。
while (-1 == send(m_clientFd, send_rpc_str.c_str(), send_rpc_str.size(), MSG_NOSIGNAL)) {
```

一行改动。它**解放了原本就存在但不可达的重连逻辑**。

## A.4 验证

同样的故障注入，修复前后对比：

| | 修复前 | 修复后 |
|---|---|---|
| 杀节点后压测进程 | **exit=141（SIGPIPE 打死）** | exit=0，正常跑完 1200 次操作 |
| 吞吐 | 无法测量 | 81 ops/s（基线 83，几乎无影响） |
| **max 延迟** | 54–60ms | **403ms** |
| 读回校验 | 无法进行 | **0 丢失，0 值错误** ✅ |

**那个 403ms 是这次修复最有价值的观察**——它就是**选举的特征时间**（`minRandomizedElectionTime`=300ms，`max`=500ms）。丢一个 follower 触发重新选主，客户端在选举期间的重试被正确记录为长尾延迟，之后自动恢复。

**如果只修了 SIGPIPE 却修坏了重试逻辑，这里会看到"数据丢失"或"集群不恢复"。** 两者都正常，说明修复是干净的。

## A.5 这个 bug 的严重性

在一个 Raft 集群里，**每个节点都会向其他节点发 RPC**。如果 `SIGPIPE` 不被处理：

```
节点 A 挂掉
  → 节点 B 向 A 发心跳，被 SIGPIPE 打死
     → 节点 C 向 B 发心跳，被 SIGPIPE 打死
        → 整个集群崩掉
```

**这不是"一个客户端进程挂了"，而是"一个节点故障会级联摧毁整个集群"。** 故障注入把这个单点故障放大成了全局故障，也正因为如此才把它逼了出来。

## A.6 面试追问

**Q：为什么 `recv` 不会触发 `SIGPIPE`？**

A：`SIGPIPE` 只在**写**一个已关闭的连接时产生。`recv` 遇到对端关闭会返回 `0`（EOF），不会发信号。

**Q：`SO_NOSIGPIPE` 和 `MSG_NOSIGNAL` 有什么区别？**

A：功能相同，平台不同。`SO_NOSIGPIPE` 是 BSD/macOS 的 socket 选项，**Linux 没有**；Linux 上的对应手段是给每次 `send` 调用传 `MSG_NOSIGNAL`。跨平台代码通常两个都用（`#ifdef` 包起来）。

另外还有第三种做法：进程启动时 `signal(SIGPIPE, SIG_IGN)` 全局忽略。**我没选它**，因为改全局信号处置是进程级的副作用，一个库不该擅自替调用方决定；`MSG_NOSIGNAL` 是局部的、显式的。

**Q：为什么不是"每次写之前先检查连接是否还活着"？**

A：做不到。TCP 的连接状态是异步的——你检查的那一刻它可能是活的，真正 `send` 时对端已经关了。**这类问题只能靠"允许写失败并处理失败"，不能靠"提前判断"。** 这也是为什么这个 bug 的修复方向是"让 send 返回错误码"而不是"避免 send 到死连接"。

**Q：这个 bug 用静态审阅能发现吗？**

A：能，但很难。`send(..., 0)` 写了太多次，扫过去不会觉得有问题。**我是被 `exit=141` 这个具体数字推着去查的**——先算出来 141 = 128+13 = SIGPIPE，再回头看代码，一眼就找到了。**有个具体的失败信号，定位是分钟级的；没有它，这个 bug 可以一直躺着。**

# 案例 B：崩溃恢复从未生效

## B.0 一句话版本

`Persister` 的构造函数用 `std::ios::trunc` 打开落盘文件——**每次进程启动都先把上次的状态抹掉**，
而紧跟在后面的"读取快照恢复状态"的代码因此永远读到空。
`persist()` / `readPersist()` / `Save()` / `ReadSnapshot()` 一行不缺，但**整套持久化从未生效过**。

而 Raft 论文 Figure 2 的持久化要求，正是"当选者必含所有已提交日志"这条**安全性保证**的基础。

## B.1 发现：一个 0 字节的文件

跑完一轮集群后，我顺手看了一眼持久化文件：

```
-rw-r--r-- 1 hxl hxl     0 raftstatePersist0.txt
-rw-r--r-- 1 hxl hxl   271 raftstatePersist1.txt
-rw-r--r-- 1 hxl hxl     0 raftstatePersist2.txt
-rw-r--r-- 1 hxl hxl     0 snapshotPersist0.txt
-rw-r--r-- 1 hxl hxl     0 snapshotPersist1.txt
-rw-r--r-- 1 hxl hxl     0 snapshotPersist2.txt
```

可疑的是：**快照文件全是 0 字节**。而配置里 `maxraftstate = 500`，快照阈值只有 50 字节，理论上应该**每 apply 一条命令就触发一次快照**。跑了上千次操作，一个快照都没落盘？

## B.2 用一个定向探针证伪/证实

光看文件大小不够——也可能是"写了但没 flush，被 `SIGKILL` 丢了"。**别猜，写个往返探针**：

```cpp
// 第一轮：模拟节点运行中写入状态
{
  Persister p(node);
  p.Save("<<RAFTSTATE-BLOB>>", "<<SNAPSHOT-BLOB>>");
}
// 第二轮：模拟进程重启（重新构造 + 读取）
{
  Persister p(node);
  std::string rs = p.ReadRaftState();
  std::string ss = p.ReadSnapshot();
  // 期望读回刚写的内容
}
```

结果：

```
[写入轮] 已调用 Save(raftstate, snapshot)
[写入轮] raftstatePersist99.txt 大小: 18
[写入轮] snapshotPersist99.txt 大小: 17     ← 写是确实写下去了
[重启轮] ReadRaftState() -> ""  (长度 0)
[重启轮] ReadSnapshot()  -> ""  (长度 0)     ← 重启后读到空
[结论] ❌ 重启后读不到任何持久化状态
```

**写入是成功的，重启后读不到。** 定位到读取路径或构造路径。

## B.3 根因（一共四处，叠加）

**① 构造函数把文件截断了**

```cpp
Persister::Persister(const int me) : ... {
  /** 检查文件状态并清空文件 */          // ← 注释已经很直白了
  std::fstream file(m_raftStateFileName, std::ios::out | std::ios::trunc);
  file.close();
  file = std::fstream(m_snapshotFileName, std::ios::out | std::ios::trunc);
  file.close();
  m_raftStateOutStream.open(m_raftStateFileName);   // ofstream 默认 mode=out，也会截断
  m_snapshotOutStream.open(m_snapshotFileName);
}
```

`std::ios::out | std::ios::trunc` 会把已存在的文件清零。而调用顺序是：

```cpp
// KvServer 构造函数
std::shared_ptr<Persister> persister = std::make_shared<Persister>(me);   // ← 状态在这里被抹掉
...
auto snapshot = persister->ReadSnapshot();       // ← 读到的必然是空
if (!snapshot.empty()) ReadSnapShotToInstall(snapshot);   // ← 死代码，永远不执行
```

**② 读取用了 `operator>>`**

```cpp
std::fstream ifs(m_raftStateFileName, std::ios_base::in);
std::string snapshot;
ifs >> snapshot;      // ← 遇第一个空白字符就停
```

而 raftstate / snapshot 是 **boost 文本归档**，内容里全是空格和换行。即使文件有内容，`>>` 也只能读到第一个词。

**③ 读完重开写流时又截断了文件**

```cpp
DEFER {
  m_snapshotOutStream.open(m_snapshotFileName);  //默认是追加      ← 这个注释是错的
};
```

`ofstream::open` 的默认 mode 是 `ios::out`，对**已存在**的文件会截断。注释写着"默认是追加"，那是误解。结果是**每次读快照都会把快照文件清零**。

**④ 写入后不 `flush`**

`m_raftStateOutStream << data;` 之后没有 `flush()`，数据停在用户态缓冲区。进程被 `SIGKILL` 时直接丢失——而 `persist()` 的语义是"**在对外响应之前必须落盘**"（Raft 要求 `votedFor` / `currentTerm` 先持久化再回复投票）。

## B.4 修复

```cpp
// ① 只确保文件存在，不清空已有内容
for (const std::string &fname : {m_raftStateFileName, m_snapshotFileName}) {
  std::ofstream probe(fname, std::ios::out | std::ios::app);   // app：不存在则建，存在则不动
  if (probe.is_open()) probe.close();
}
// 写流也必须用 app，否则 open 时就会截断
m_raftStateOutStream.open(m_raftStateFileName, std::ios::out | std::ios::app);
m_snapshotOutStream.open(m_snapshotFileName, std::ios::out | std::ios::app);
// 已有内容要计入大小，否则快照触发时机会失准
std::ifstream in(m_raftStateFileName, std::ios::in | std::ios::binary | std::ios::ate);
if (in.is_open()) m_raftStateSize = static_cast<long long>(in.tellg());

// ② 整文件读取
std::stringstream ss;
ss << ifs.rdbuf();               // 而不是 ifs >> str

// ③ DEFER 里重开写流也要用 app
DEFER { m_snapshotOutStream.open(m_snapshotFileName, std::ios::out | std::ios::app); };

// ④ 写完 flush
m_raftStateOutStream << data;
m_raftStateOutStream.flush();
```

## B.5 验证

探针：

```
[重启轮] ReadRaftState() -> "<<RAFTSTATE-BLOB>>"  (长度 18)
[重启轮] ReadSnapshot()  -> "<<SNAPSHOT-BLOB>>"  (长度 17)
[结论] ✅ 读回了持久化状态
```

实跑集群后看文件：`raftstatePersist*.txt` 从**恒为 0 字节**变成 380 / 380 / 160 字节，`snapshotPersist*.txt` 从 0 变成 ~7.8KB。

## B.6 一个需要留意的行为变化

**开启持久化之后，节点重启会真的恢复状态了**（此前永远从空白开始）。

这不是"修好了一个小问题"——它改变了系统的可观测行为。所以我在压测脚本里默认清空持久化文件（`CLEAN_STATE=0` 可保留，用来验证恢复路径）。**修复引入的行为变化必须被显式管理，否则它会在别处制造新的困惑。**

## B.7 面试追问

**Q：这个 `trunc` 会不会是作者有意为之，为了让每次 demo 都从干净状态跑？**

A：这个怀疑是合理的，我一开始也有。但**同一份代码里两处意图是矛盾的**：`Persister` 把文件清空，而 `KvServer` 构造里又专门写了"读快照 → 恢复状态机"的逻辑。如果作者真的想每次清空，那段读取代码就是死的。**两处必有一处是错的。** 而 Raft 的安全性是强依赖持久化的，所以我判断 `Persister` 是错的那一方。

**Q：`flush()` 够吗？不需要 `fsync()` 吗？**

A：`flush()` 只把数据从用户态缓冲区推进内核页缓存；**抗断电还需要 `fsync()`**。我给这个项目加的是 `flush()`——因为原问题（`SIGKILL` 丢失）它就能解决，而 `fsync` 每条命令一次会严重拖慢吞吐。真实系统里会用 group commit 来摊销 `fsync` 的开销。

严格说，要做到 Raft 论文要求的持久化语义，是**需要 `fsync` 的**。这是我在这个项目里做的一个取舍，我认为面试时应该主动说明。

**Q：为什么持久化对 Raft 是"必需"而不是"优化"？**

A：因为**选举安全性**依赖它。具体地：节点在 `term=T` 给候选人 A 投了票，如果这个 `votedFor` 没有落盘，节点崩溃重启后 `votedFor=-1`，它可能**在同一个 term 里又给 B 投一票**。两个候选人都拿到多数派 → **一个 term 出现两个 leader** → 日志分叉。

这就是论文 Figure 2 把 `currentTerm` / `votedFor` / `log[]` 标为"持久化状态（必须先于响应落盘）"的原因。

**Q：你怎么知道修复没有引入新问题？**

A：三层验证：① 探针做往返测试；② 实跑集群后确认文件真的有了内容；③ 重跑全部压测确认没有性能回归（82 ops/s、P50 20.5ms，与修复前一致）并读回校验通过。

# 三个案例的横向对比（这段可以直接在面试里讲）

同一个项目，三种不同的缺陷，靠**三种不同的手段**分别发现：

| 案例 | 缺陷类型 | 发现手段 | 为什么别的办法发现不了 |
|---|---|---|---|
| 一（静默丢写） | 正确性 / 线性一致 | **读回校验** | 只看 QPS 完全正常；响应也是 `OK` |
| A（SIGPIPE） | 可靠性 / 进程生命周期 | **故障注入** | 静态读代码看不出 `send(...,0)` 有问题；无故障时永远不触发 |
| B（持久化失效） | 耐久性 / 崩溃恢复 | **定向往返探针** | 不重启就永远不知道恢复不了 |

**三条结论，我认为比任何一个具体 bug 都重要：**

1. **"跑得通"和"是对的"之间隔着一整个测试策略。** 这个项目能编译、能跑、demo 能出结果、QPS 曲线也正常——但它的崩溃恢复从未生效，两个客户端共存时会丢数据。

2. **不同的缺陷需要不同形状的验证。** 读回校验抓不到 SIGPIPE，故障注入抓不到持久化失效。**没有一种"通用压测"能覆盖全部。**

3. **给每个不变量写一条断言。** 上面三个案例，本质上是三条不变量被违反：
   - 客户端收到 `OK` ⇒ 数据可读
   - 对端不可用 ⇒ 本端不能死
   - 落盘成功 ⇒ 重启后能读回

   把不变量写成可执行的检查，比"多加几个测试用例"更有针对性。
