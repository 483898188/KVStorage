  链路 3：读（Get）

  形状和写几乎一样，但有两处差别（kvServer.cpp 的 Get 2 参数版）：

  1. op.Operation = "Get"，同样走 m_raftNode->Start → raft 复制 → apply。读也过共识，这是本实现保证线性一致的方式（不是从本地 SkipList 直接读）。
  2. 超时分支有本地快速路径：timeOutPop 超时后，若 ifRequestDuplicate(op.ClientId, op.RequestId) && 自己仍是 leader，说明这条 Get 早先已提交过，于是直接本地 ExecuteGetOpOnKVDB  
     返回，不算违反线性一致。否则回 ErrWrongLeader 让 clerk 换节点。

  Clerk::Get 的重试循环和 Put 一样：!ok || ErrWrongLeader → server = (server+1)%n，requestId 不变。

  链路 4：选举

  electionTimeOutTicker (协程)                                 // raft.cpp
    1. while (m_status == Leader) usleep(HeartBeatTimeout);   // leader 不参选
    2. 睡 suitableSleepTime = 随机选举超时 + m_lastResetElectionTime - now()
    3. 醒来若 m_lastResetElectionTime 没被重置过 → doElection()

    2. votedNum = make_shared<int>(1);                        // 自己一票
    3. m_lastResetElectionTime = now();

  对端：Raft::RequestVote(5) → RequestVote(2)：检查 term；用 UpToDate(index, term) 判断候选人日志是否够新；投过且不是投给它就拒；否则记 m_votedFor

  发起方 sendRequestVote 收到回复：

    if (!reply.votegranted) return;

  doHeartBeat 一发出，followers 的选举计时器被重置，集群稳定下来。

  链路 5：日志冲突回退（leader 落后于 follower 时）

  上一条链路的"复制"里只走了成功分支。失败分支是 raft 的性能核心：

  leader: reply.success == false → m_nextIndex[server] = reply.updatenextindex
          （回退多少由 follower 算，不是无脑 -1）

  follower 侧 AppendEntries1 给的三种回退值：
    a) prevlogindex > lastLogIndex          → lastLogIndex + 1
    b) matchLog 失败（index 对 term 不对）  → 从 prevlogindex 往前扫，
                                              找 term 变化的第一个位置 + 1
    c) prevlogindex < lastSnapshotIncludeIndex → snapshotIdx + 1

  其中 (c) 那段有个真实的地雷：代码里显式 return，注释写明了原因——如果不 return 会落到 matchLog()，而 matchLog 里有 myAssert(logIndex >= m_lastSnapshotIncludeIndex)，myAssert   
  的实现是 std::exit(EXIT_FAILURE)（src/common/util.cpp:8），即整个节点进程直接退出。触发条件是"follower 的快照比 leader 认为的更新"，属于正常的落后/恢复场景。

  链路 7：leader 挂掉 → 客户端重试 → 新 leader

  这是把链路 2 和链路 4 串起来才知道为什么要那样写：

  1. leader 进程死了（或网络分区）
  2. 它不再发心跳 → followers 的 electionTimeOutTicker 陆续超时
     → doElection → 新 term 选举 → 新 leader（多数派）
  3. 客户端此刻手里 m_recentLeaderId 还指着死节点
     → PutAppend 的 RPC !ok（连接失败）或 reply.err()==ErrWrongLeader
  4. Clerk::PutAppend: server = (server+1) % n，requestId 不变，continue
     → 一路试到新 leader → OK
  5. 如果这条 op 其实在旧 leader 上已经提交、只是应答丢了：
     新 leader 的 GetCommandFromRaft 里 ifRequestDuplicate(clientId, requestId) 命中
     → 跳过执行，但 SendMessageToWaitChan 照常唤醒 → 返回 OK

  第 5 步就是整个系统线性一致的落点：在同一 RequestId 上重试是安全的，去重责任在状态机（m_lastRequestId[clientId]），不在客户端。而 m_lastRequestId
  会被序列化进快照（kvServer.h:111 的 ar & m_lastRequestId），所以重启后去重表不会丢——否则重启会导致重复写。
