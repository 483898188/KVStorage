# 面试案例：一个静默丢数据的线性一致性缺陷

> 项目：自研 Raft 共识 + 分布式 KV（`KVstorageBaseRaft-cpp`）
> 角色：自建压测与正确性验证工具，发现问题并定位、修复
> 相关代码：`src/raftClerk/include/clerk.h`、`src/raftCore/kvServer.cpp`
> 复现脚本：`benchmark/dedup_test.sh`

---

## 0. 一句话版本

**两个客户端进程连同一个 Raft KV 集群时，后一个进程的所有写入被服务端当成重复请求丢弃，而客户端每一次都收到 `OK`。**
根因是客户端 ID 生成用了 `rand()` 却没有 `srand()`，导致每个进程拿到完全相同的 `clientId`；
服务端的去重表据此把新客户端的请求全部判重。表现为**静默的数据丢失 + 虚假的成功响应**，即线性一致性被破坏。

实测：第二个进程 **300/300 次写入全部丢失，全部返回成功**。

---

## 1. 背景：这个系统的去重机制

要讲清楚这个 bug，得先解释 Raft KV 的"恰好一次"语义是怎么实现的。

Clerk（客户端库）的重试循环长这样（`clerk.cpp`）：

```cpp
void Clerk::PutAppend(std::string key, std::string value, std::string op) {
  m_requestId++;                  // ① 每次"新操作"才自增
  auto requestId = m_requestId;   // 整个 while 里不变
  auto server = m_recentLeaderId;
  while (true) {
    args.set_clientid(m_clientId);
    args.set_requestid(requestId);
    bool ok = m_servers[server]->PutAppend(&args, &reply);
    if (!ok || reply.err() == ErrWrongLeader) {   // ② 换一台重试，requestId 不变
      server = (server + 1) % m_servers.size();
      continue;
    }
    if (reply.err() == OK) return;
  }
}
```

**关键设计**：重试时 `requestId` 刻意不变。因为网络可能丢响应——请求其实已经执行了，只是响应没回来。如果重试用新 ID，`Append` 就会被执行两次。

所以契约是：**客户端保证"重试用同一个 ID"，服务端保证"同一个 ID 只执行一次"**。服务端侧（`kvServer.cpp`）：

```cpp
bool KvServer::ifRequestDuplicate(std::string ClientId, int RequestId) {
  std::lock_guard<std::mutex> lg(m_mtx);
  if (m_lastRequestId.find(ClientId) == m_lastRequestId.end()) return false;
  return RequestId <= m_lastRequestId[ClientId];    // ← 单调序列，用 <=
}
```

`m_lastRequestId[clientId]` 记录该客户端**最后执行的** `RequestId`。因为客户端单调递增，所以 `RequestId <= 记录值` 就意味着"这是重复请求"。

这套机制本身是对的，**是 Raft 客户端语义的标准做法**。问题出在 `clientId` 从哪来。

---

## 2. 发现：一次压测的校验失败

我写了一个压测客户端，**除了测吞吐，还做全量读回校验**：

```cpp
// 写完所有 key 之后，逐个读回比对
for (int t = 0; t < nThreads; ++t) {
  Clerk clerk; clerk.Init(cfg);
  for (int i = 0; i < nOps; ++i) {
    std::string got = clerk.Get(keyOf(t, i));
    if (got.empty())        ++missing;   // 写进去的 key 读不到
    else if (got != valOf(t, i)) ++wrong; // 读到了别的值
  }
}
```

之所以加这个校验，是因为**QPS 数字好看不代表系统是对的**。对一个共识系统来说，"已确认的写入丢了"比"吞吐低十倍"严重得多。

第一次跑，8 线程 × 500 次操作（一个集群内连续跑了 1/2/4/8 线程四轮）：

```
[校验] 检查 4000 个 key：丢失 3500，值错误 0
[校验] ❌ 失败 —— 存在丢写或数据损坏
```

**3500/4000 丢失，只剩 500 个。** 而 500 恰好等于"一个线程写满的量"——这个"恰好"很可疑。

---

## 3. 第一次假设，以及它是怎么被证伪的

我的第一反应：**所有 8 个线程的 Clerk 拿到了相同的 `clientId`**。

理由：`Clerk::Uuid()` 是这样的——

```cpp
std::string Uuid() {
  return std::to_string(rand()) + std::to_string(rand())
       + std::to_string(rand()) + std::to_string(rand());
}
```

`rand()` **从不 `srand()`**。8 个线程并发构造 Clerk → 32 次 `rand()` 竞争同一个全局 PRNG（glibc 的 `rand()` 不是线程安全的）→ 可能拿到相同值。

如果 8 个 Clerk 共享一个 `clientId`，那服务端的去重表会接受 thread 0 的 `requestId` 1..500，然后拒绝其余 7 个线程的 1..500（全都 `<= 500`）。**恰好剩 500 个**——与观测吻合。

### 但我的实验有混淆变量

冷静下来复盘，我意识到：

- 那个 scaling 脚本是**在同一个集群上连续跑了四轮**（1/2/4/8 线程）
- key 空间是 `k_<线程>_<序号>`，四轮之间**重叠**
- 而**去重表 `m_lastRequestId` 是跨进程持续存在的**（它随集群长期存活）

三重混淆叠在一起，我没法把锅扣在"线程间 clientId 碰撞"上。

**于是我设计了对照实验**：每次都用**全新集群**，只跑单轮。

| 线程数 | 结果 |
|---:|---|
| 1 | 丢失 0，值错误 0 ✅ |
| 2 | 丢失 0，值错误 0 ✅ |
| 4 | 丢失 0，值错误 0 ✅ |

**假设被证伪了。** 干净集群下多线程完全正常——因为同一进程内的 Clerk 会依次消耗 `rand()` 序列，拿到不同的值。

> 这一步是整件事的转折点。如果我当时直接按第一个假设去改代码，会改错地方，
> 而且那个"3500"会变成一个我永远没解释清楚的悬案。

---

## 4. 修正假设，并设计一个能给出决定性证据的实验

重新看那三条线索：

1. `Uuid()` 没有 `srand()` → **每个进程**的 `rand()` 序列相同
2. 去重表 `m_lastRequestId` 跨进程持续存在
3. 我的 scaling 脚本是**多个客户端进程**打同一个集群

把 1+2+3 连起来：

> 第一个 bench 进程拿到 `clientId = X`，写满 `requestId` 1..500，去重表记下 `m_lastRequestId[X] = 500`。
> 第二个 bench 进程**拿到同样的 `clientId = X`**（因为无 `srand()`，序列完全相同），
> 它的 `requestId` 1..500 **全都 `<= 500`** → 全被判为重复 → 全不执行。
> 但服务端的去重路径**照样唤醒等待的 RPC 线程并回 `OK`** → 客户端以为成功了。

要证明这个假设，需要**同一个集群 + 两个客户端进程 + 能让"写入是否真的发生"可观测**。

难点在于：如果两个进程写同样的 key、同样的 value，即使写丢了也**看不出来**（旧值和新值相同）。

**所以我给压测程序加了一个值前缀选项**，让两次运行写入可区分的值：

```cpp
std::string g_valPrefix;
std::string valOf(int t, int i) {
  return g_valPrefix + "v_" + std::to_string(t) + "_" + std::to_string(i);
}
```

然后：**只启动一次集群**，先后跑两个客户端进程，`-p A1_` 和 `-p B2_`。

判断标准很干净：如果进程 #2 的写入真的发生了，`Get` 应当返回 `B2_v_*`；如果被丢弃，返回的会是进程 #1 写的 `A1_v_*` → 报**"值错误"**。

---

## 5. 决定性证据

```
############ 客户端进程 #1：值前缀 = A1 ############
[校验] 检查 300 个 key：丢失 0，值错误 0
[校验] ✅ 通过

############ 客户端进程 #2：同一个集群，值前缀 = B2 ############
[校验] 检查 300 个 key：丢失 0，值错误 300
[校验] ❌ 失败 —— 存在丢写或数据损坏
```

**`值错误 300` —— 300/300。**

进程 #2 的每一次 `Put` 都返回了 `OK`，但没有一条写进去；300 个 key 上存的全都还是进程 #1 的值。

根因确认。

---

## 6. 为什么这个 bug 一直没被发现

这一点我认为比 bug 本身更值得讲：

**① 它返回成功。** `PutAppend` 返回 `OK`，客户端没有任何理由重试。上层应用拿到成功响应，数据却没落。这是**线性一致性违规**，不是"性能问题"或"偶发失败"。

**② 它只在跨进程时触发。** 同一个进程内建多个 `Clerk` 完全正常（`rand()` 序列在推进）。所有单进程的测试、demo 都测不出来。

**③ 触发条件极其平常。** 任何两个客户端进程共存于同一集群即可：第二次运行 `callerMain`、客户端重启、两个用户同时使用、一个应用起多副本——**全部会静默丢数据**。

**④ 项目自带的 demo 恰好绕过了它。** `example/raftCoreExample/caller.cpp` 每次跑一个进程、跑完就退，从没出现过"第二个客户端"。而它的输出只 `printf` 不校验：

```cpp
std::string get1 = client.Get("x");
std::printf("get return :{%s}\r\n", get1.c_str());   // 只打印，从不比对
```

**⑤ 静态读代码很容易放过它。** `Uuid()` 那四行看起来就是"生成个随机 ID"，不像有问题的代码。真正的问题是它和**另一个模块**（`KvServer` 的去重表）的语义组合——这类跨模块的缺陷，光读单个函数是读不出来的。

## 7. 修复

```cpp
// src/raftClerk/include/clerk.h
//
// 原实现：to_string(rand()) 拼四次，但从未调用 srand()，
// 于是每个进程拿到的 rand() 序列完全相同 —— 两个客户端进程会得到同一个 clientId。
// 服务端 m_lastRequestId[clientId] 里已存有第一个进程的进度，
// 第二个进程的 RequestId 一律 <= 该值，被判为重复而不执行，却仍然返回 OK —— 静默丢写。
std::string Uuid() {
  static std::mutex mtx;
  static std::mt19937_64 rng{std::random_device{}() ^
                             (static_cast<uint64_t>(::getpid()) << 32) ^
                             static_cast<uint64_t>(
                                 std::chrono::steady_clock::now().time_since_epoch().count())};
  std::lock_guard<std::mutex> lg(mtx);
  return std::to_string(rng()) + std::to_string(rng());
}
```

三个改动点，各自有理由：

| 改动 | 解决什么 |
|---|---|
| `std::random_device` 播种 | 熵来自内核，**跨进程不会相同**（原实现的根本问题） |
| 混入 `getpid()` 与单调时钟 | `random_device` 理论上仍可能撞；混入进程身份后碰撞概率再降一档 |
| `static` + `std::mutex` | 同进程内多线程也安全（原 `rand()` 本身就不是线程安全的） |

### 验证

```
客户端进程 #2：校验 300 个 key：丢失 0，值错误 0    ✅
```

修复前后各跑一遍 `benchmark/dedup_test.sh`，这是可复现的回归测试。

## 8. 面试官可能会追问什么

**Q：为什么 `rand()` 不 `srand()` 会在每个进程产生相同序列？**

A：glibc 的 `rand()` 在未调用 `srand()` 时，行为等价于 `srand(1)`——种子固定，序列就固定。所以任何两个进程，只要调用 `rand()` 的顺序和次数一致，拿到的值就完全一样。

**Q：为什么同一进程内多线程就没问题？**

A：因为全局 PRNG 的状态是共享的，线程 A 消耗掉 4 个值之后，线程 B 拿到的是第 5-8 个。真正危险的是并发调用（`rand()` 不是线程安全的，可能读到撕裂的状态），但即使拿到重复值，也只是同进程内两个 Clerk 撞——那是我最初的假设，实测被证伪了。

**Q：这个修复够吗？还有什么隐患？**

A：对这个项目够用。但要说透的话，有三点：

1. **根因其实是"客户端自己生成身份"这个设计。** 更稳妥的是服务端发放 ID，或者客户端带一个持久的会话标识（session/epoch），崩溃重启后仍然唯一。
2. **去重表 `m_lastRequestId` 无上限增长**——每个客户端一条记录，永不清理。客户端多了就是内存泄漏。
3. **`m_requestId` 是 `int`，溢出后会回绕**，`(clientId, requestId)` 的唯一性就不成立了。真实系统里会用 64 位 + 定期换 epoch。

**Q：服务端对重复请求返回 `OK` 是错的吗？**

A：不是。**幂等重试返回成功是正确的**——这正是"恰好一次"语义的实现方式。错的不是去重逻辑，而是两个不同客户端被识别成了同一个。

**Q：如果服务端不回 `OK` 而是报错，这个 bug 会被发现吗？**

A：会早得多，但那会破坏正确的重试语义。更好的做法是让**重复请求的判定带上"这是不是我刚才那个请求"的信息**，而不是仅凭 `(clientId, requestId)` 单调比较——比如客户端重试时携带一个 attempt 编号。

**Q：你怎么保证下次不会再有这类 bug？**

A：三条：

1. **正确性校验而不是只看性能**。这个 bug 是靠"写完读回比对"抓到的，不是靠 QPS 曲线。压测只测吞吐的话，它会一直藏着。
2. **故障注入**。我后来加的 `kill -9` 一个节点，又直接暴露出另一个问题（下面那条）。
3. **让不变量可断言**。"客户端收到 OK ⇒ 数据可读"是可以在测试里直接断言的不变量。

## 附：这条调查线的连带收获

同一个压测工具后续还暴露了两个同类问题，说明**"能跑通"和"是对的"之间差距很大**：

**① 杀一个节点，客户端进程直接被打死（exit=141 = 128+SIGPIPE）**

`MprpcChannel` 用 `send(fd, ..., 0)` 向已被关闭的 socket 写数据，内核发 `SIGPIPE`，默认动作是终止进程。于是它下面那段"send 失败就重连重发"的逻辑**永远执行不到**——进程在那之前就死了。

修复是加 `MSG_NOSIGNAL`。修完再跑故障注入：

| | 修复前 | 修复后 |
|---|---|---|
| 杀节点后压测进程 | exit=141（信号打死） | exit=0，正常完成 |
| max 延迟 | 54–60ms | **403ms**（选举的特征） |
| 校验 | 无法完成 | 0 丢失 0 错误 ✅ |

**② 崩溃恢复从未生效**

我写了个往返探针：调 `Save(raftstate, snapshot)` 落盘 → 析构 → 重新构造 → 读回。

```
[写入轮] 文件确实写了：18 字节 / 17 字节
[重启轮] ReadRaftState() -> ""   (长度 0)
[结论] ❌ 重启后读不到任何持久化状态
```

原因是 `Persister` 构造函数用 `std::ios::trunc` 打开两个文件——**每次启动都先把上次的状态抹掉**，而 `KvServer` 构造里紧接着就要读它。读的必然是空的。

**这条比第一个更严重**：Raft 论文 Figure 2 要求的持久化，是"当选者必含所有已提交日志"这条安全性保证的基础。持久化不生效 = 这个保证在崩溃后不成立。

修复涉及四处（取消构造时截断、改用 `app` 模式重开写流、整文件读取而非 `operator>>`、写入后 `flush`），修完探针通过。

---

## 这个案例想传达的几件事

1. **压测的价值在正确性校验，不在 QPS 数字。** 这条 bug 只在"写完读回比对"下才现形。
2. **假设被证伪是有价值的进展，不是失败。** 我第一次猜"线程间 clientId 碰撞"是错的；正因为做了对照实验否掉它，才被迫去找真正的解释。
3. **实验设计比结论更重要。** 加上 `-p` 值前缀这个小小的改动，把一个"看不出差别"的场景变成了决定性证据。
4. **跨模块的语义组合是静态审阅的盲区。** 单看 `Uuid()` 或单看 `ifRequestDuplicate()` 都很正常，问题出在两者的契约上。
5. **"实现了"和"生效了"是两回事。** `Persister` 里持久化的代码一行不少，但构造函数把文件清空了，所以从来没生效过。
