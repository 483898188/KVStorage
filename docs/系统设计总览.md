## 1. 一句话概括与技术栈

**从零手写的 Raft（教学实现）+ 一个线性一致的 KV 状态机**，跑在自研的 protobuf RPC 框架上，用 epoll + 有栈协程做运行时。

| 组件 | 选型 | 是否自研 |
|---|---|---|
| 共识 | Raft（论文实现的简化版） | ✅ |
| 状态机 | 跳表 `SkipList<string, string>` | ❌ 取自「代码随想录」 |
| RPC | mprpc（基于 muduo + protobuf） | ✅ |
| 协程 | monsoon（ucontext 有栈协程 + hook） | ❌ 取自 sylar 教程 |
| 序列化 | protobuf（RPC 层）+ boost text archive（Op / 快照） | — |
| 构建 | CMake ≥ 3.22，C++20 | — |
| 依赖 | muduo、protobuf、boost、pthread、dl | — |

**代码量**：`src/` 手写约 7000 行，其中生成代码（`*.pb.*`）另有 8300 行。
**有效学习面积约 2000 行**（`raft.cpp` 占一半以上）。

## 2. 分层架构

```
┌───────────────────────────────────────────────────────────────┐
│  用户程序 (example/raftCoreExample/caller.cpp)                 │
└───────────────────────────┬───────────────────────────────────┘
                            │ Put / Get / Append
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  Clerk  (src/raftClerk)                                        │
│   · 重试循环：ErrWrongLeader → 换一台服务器，requestId 不变      │
│   · 缓存"我以为是 leader 的那台"                                │
│   · 完全不知道 Raft 的存在                                      │
└───────────────────────────┬───────────────────────────────────┘
                            │ kvServerRPC.proto: Get / PutAppend
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  mprpc  (src/rpc)                                              │
│   · MprpcChannel：序列化 → [varint|RpcHeader|args] → TCP        │
│   · RpcProvider：注册 service / 按名字分发 / 回响应             │
│   · 自定义二进制协议，跑在 muduo TcpServer 上                   │
└───────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  KvServer  (src/raftCore/kvServer.cpp)                         │
│   · 把客户端 RPC 转成 Raft 提案                                 │
│   · 去重表 m_lastRequestId[clientId]                            │
│   · waitApplyCh：RPC 线程在这里等自己的日志被 apply             │
└───────────────────────────┬───────────────────────────────────┘
                            │ Raft::Start(Op)  ▲ ApplyMsg
                            ▼                  │ (applyChan)
┌───────────────────────────────────────────────────────────────┐
│  Raft  (src/raftCore/raft.cpp)                                 │
│   · 选举 / 日志复制 / commitIndex 推进 / 快照 / 持久化           │
│   · 只把日志当 string 搬运，不关心内容                          │
└───────────────────────────┬───────────────────────────────────┘
                            │ raftRPC.proto: AppendEntries / RequestVote / InstallSnapshot
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  Persister (落盘)      │      monsoon 协程库 (定时器)           │
└───────────────────────────────────────────────────────────────┘
```

**核心不变式**：`Raft` 完全不知道 `Op` 里是什么，它只看到 `LogEntry.Command` 这个 `string`。
这是"共识层可复用、状态机可替换"的基础。

## 4. 核心数据流

### 4.1 写请求（Put / Append）

```
① Clerk::PutAppend                        clerk.cpp:41
   m_requestId++                          ← 只在"新操作"时自增
   requestId 在整个重试循环内不变

② KvServer::PutAppend(controller,...)     kvServer.cpp:365   ← protobuf RPC 入口
   └── KvServer::PutAppend(args, reply)   kvServer.cpp:212
       构造 Op{Operation, Key, Value, ClientId, RequestId}

③ Raft::Start(op, &index, &_, &isLeader)  raft.cpp:947
   if (!isLeader) → 回 ErrWrongLeader，结束
   否则：追加 LogEntry 到 m_logs，persist()，返回 index

④ 在 waitApplyCh[index] 注册一个 LockQueue<Op>
   然后 timeOutPop(CONSENSUS_TIMEOUT) 阻塞等待
   ⚠️ 此处释放 KvServer::m_mtx —— 不能持锁等待

⑤ 【后台】leaderHearBeatTicker 每 25ms 触发一次 doHeartBeat
   doHeartBeat → sendAppendEntries → AppendEntries1（follower 追加日志）
   多数派确认后推进 m_commitIndex
   ⚠️ Raft::Start 自己不触发复制，必须等心跳

⑥ 【后台】applierTicker 每 10ms 轮询
   getApplyLogs() 把 [m_lastApplied+1, m_commitIndex] 转成 ApplyMsg
   applyChan->Push(msg)

⑦ 【后台】ReadRaftApplyCommandLoop（独立线程，阻塞在 applyChan->Pop()）
   GetCommandFromRaft(msg)                kvServer.cpp:166
     · ifRequestDuplicate(clientId, requestId) → 重复则跳过执行
     · 否则 ExecutePutOpOnKVDB → SkipList::insert_set_element
     · SendMessageToWaitChan(op, index)  ← 唤醒 ④ 中阻塞的线程

⑧ ④ 的线程被唤醒，比对 clientId/requestId，回 OK
```

**三个衔接点值得单独记**：

| 点 | 位置 | 作用 |
|---|---|---|
| `waitApplyCh[index]` | `kvServer.h:38` | RPC 线程与 apply 线程的会合点 |
| `applyChan` | `raft.h:55` | Raft → KvServer 的唯一通道 |
| `m_commitIndex` 推进 | `sendAppendEntries` 内联逻辑 | 由心跳驱动，不是由 `Start` 驱动 |

### 4.2 读请求（Get）

**读也走完整共识**——`KvServer::Get` 同样调 `Raft::Start`（`kvServer.cpp:90`）。

```
Get → Op{Operation="Get"} → Raft::Start → 复制 → apply → 回 value
```

这是**最朴素但最昂贵的线性一致读**：每次读都要写一条日志、等多数派复制。

**为什么 `GetCommandFromRaft` 里没有 "Get" 分支？** 因为 Get 不改状态机——
它的值是在 RPC 线程里直接读 SkipList 拿到的（`ExecuteGetOpOnKVDB`），
apply 循环对 Get 只做两件事：推进去重表、唤醒等待者。

**Get 的超时路径**（`kvServer.cpp:112-135`）值得注意：超时后如果
`ifRequestDuplicate(...) && isLeader`，就直接本地读并返回——论证是"已提交过的 Get 必然已被 apply 过，本地重放不违反线性一致性"。

### 4.3 选举

```
electionTimeOutTicker（协程，electionTimeOutTicker 循环）
  └─ 睡到 (m_lastResetElectionTime + 随机超时)，醒来检查是否被续期
       └─ 未续期 → doElection()                    raft.cpp:202
            ├─ m_status = Candidate; m_currentTerm++; m_votedFor = me; persist()
            └─ 对每个 peer 起一个 std::thread → sendRequestVote
                 ├─ RequestVote RPC（对方：RequestVote 服务端实现 raft.cpp:611）
                 │    ├─ term 小 → 拒绝
                 │    ├─ term 大 → 三变
                 │    ├─ !UpToDate(候选人的日志) → 拒绝   ← 选举安全性的核心
                 │    └─ 已投给别人 → 拒绝；否则授票
                 └─ 收到票 → *votedNum++
                      多数派 → m_status = Leader
                              初始化 nextIndex = lastLogIndex+1, matchIndex = 0
                              立即起线程 doHeartBeat() 宣告
```

**随机化选举超时**（300–500ms）避免选票瓜分。**心跳周期 25ms** 比它小一个数量级。

### 4.4 日志复制

```
doHeartBeat（leader 每 25ms）                raft.cpp:247
  └─ 对每个 peer：
       ├─ nextIndex ≤ lastSnapshotIncludeIndex → 改发快照 leaderSendSnapShot
       └─ 否则构造 AppendEntriesArgs
            prevLogIndex/prevLogTerm = getPrevLogInfo(i)
            entries = m_logs[prev 之后全部]
            leaderCommit = m_commitIndex
            └─ 起线程 sendAppendEntries          raft.cpp:828  【响应处理】
                 ├─ reply.term > currentTerm → 三变
                 ├─ !success → m_nextIndex[server] = reply.updatenextindex  【回退优化】
                 └─ success → matchIndex = max(matchIndex, prev+len)
                              appendNums++
                              多数派 ∧ 最后一条是当前 term → 推进 commitIndex
```

**follower 侧**：`AppendEntries1`（`raft.cpp:8`）——最容易读错的一个函数：

```
① args.term < currentTerm        → 拒绝（updatenextindex = -100，特殊值）
② DEFER { persist(); }
③ args.term > currentTerm        → 三变
④ m_status = Follower            ← candidate 收到同 term 的 AE 要转变
⑤ m_lastResetElectionTime = now()  ← 重置选举定时器
⑥ prevLogIndex > lastLogIndex    → 拒绝
   prevLogIndex < lastSnapshotIncludeIndex → 拒绝
⑦ matchLog(prevIndex, prevTerm)?
     是 → 逐条比对 entries：超出则追加；index 相同 term 不同则覆盖
          推进 commitIndex = min(leaderCommit, lastLogIndex)
     否 → 往前找 term 矛盾的第一个位置，回传 updatenextindex（回退优化）
```

**本实现最重要的一个偏离论文之处**：冲突时不直接截断 follower 的日志，
而是**逐条比对后覆盖**（`raft.cpp:71-96`）。原因写在注释里：

> 不能直接截断，必须一个一个检查，因为发送来的 log 可能是之前的，
> 直接截断可能导致"取回"已经在 follower 日志中的条目。

这是为了容忍 **RPC 乱序/延迟**，代价是代码复杂化。

### 4.5 快照与恢复

**三个方向**：

| 场景 | 函数 | 说明 |
|---|---|---|
| 服务层告诉 Raft "我打了快照" | `Raft::Snapshot` | raft.cpp:1087 |
| leader 主动给落后的 follower 发 | `Raft::leaderSendSnapShot` | raft.cpp:528 |
| follower 接收安装 | `Raft::InstallSnapshot` | raft.cpp:420 |

**触发**：`KvServer::IfNeedToSendSnapShotCommand`，判据是
`GetRaftStateSize() > m_maxRaftState / 10.0`，在 `GetCommandFromRaft` 里**每 apply 一条命令检查一次**。

**快照内容由服务层定义**（`kvServer.h:114`）：

```cpp
std::string getSnapshotData() {
    m_serializedKVData = m_skipList.dump_file();   // 跳表整体 → 字符串
    boost::serialize(*this);                        // { m_serializedKVData, m_lastRequestId }
    ...
}
```

**去重表 `m_lastRequestId` 必须进快照**——否则恢复后无法去重，重复请求会被再次执行。

**Raft 只负责传递快照字节流**，不解析它。

## 5. 五个关键契约

这是理解整个系统的钥匙。每一层之间都有一个明确的接口约定：

| # | 契约 | 甲方 | 乙方 | 内容 |
|---|---|---|---|---|
| 1 | **`(clientId, requestId)`** | Clerk | KvServer | 重试期间不变；服务端据此实现"恰好一次" |
| 2 | **`Op`** | KvServer | Raft | 对 Raft 只是 `string`；boost text archive 序列化 |
| 3 | **`ApplyMsg`** | Raft | KvServer | `CommandValid` / `SnapshotValid` 两种形态 |
| 4 | **快照字节流** | KvServer | Raft + Persister | 格式由服务层定义，Raft 只搬运 |
| 5 | **`RpcHeader`** | mprpc 客户端 | mprpc 服务端 | `service_name` + `method_name` + `args_size` |

**契约 1 是整个系统线性一致性的核心**，也是产生过最严重缺陷的地方
（见[面试案例（一）](./面试案例-静默丢写.md)）。

## 6. 并发模型

### 6.1 进程与线程

**每个 `KvServer` 节点进程**（3 节点即 3 个进程，由 `raftCoreRun` fork）：

| 线程/协程 | 数量 | 来源 | 干什么 |
|---|---:|---|---|
| 主线程 | 1 | `main` | 构造 `KvServer`，最后 `join` 在 apply 循环上（**永不返回**） |
| muduo 事件循环 | 1 | `provider.Run()` | 接收 RPC |
| muduo 工作线程 | 4 | `setThreadNum(4)` | 处理 RPC 回调 |
| **IOManager 工作线程** | 1 | `Raft::init` | 跑**两个协程**（见下） |
| `applierTicker` | 1 | `Raft::init` | 每 10ms 轮询提交 |
| **瞬时线程** | 每 peer 一个 | `doHeartBeat` / `doElection` / `sendRequestVote` | detached，发完即退 |

**两个协程**（跑在 1 个 IOManager 线程上）：

```
leaderHearBeatTicker   ← while(true)，doHeartBeat 后 usleep(25ms) → 被 hook 成"让出"
electionTimeOutTicker  ← while(true)，usleep(随机选举超时) → 同样让出
```

**⚠️ 这是整个并发模型里最需要注意的地方**：25ms 心跳 × 3 节点 →
**leader 每秒创建约 80 个 `std::thread`**。线程创建要走 `clone()` 系统调用，
开销远大于协程切换——**引入 `fiber` 省下的线程开销，被这里又花回去了**。

`raft.cpp:1031` 的作者注释也承认这是实验性的。

### 6.2 三个层次的锁

| 锁 | 保护什么 | 实现 |
|---|---|---|
| `Raft::m_mtx` | Raft 全部状态 | `std::mutex`（**未被 hook**） |
| `KvServer::m_mtx` | `waitApplyCh` / `m_lastRequestId` / `m_skipList` | `std::mutex` |
| `SkipList::_mtx` | 跳表自身 | `std::mutex`（**但 search/dump 不加锁**） |

**`std::mutex` 未被 hook 是协程模型下的一个隐患**：如果协程在持锁时让出，
另一个协程抢同一把锁会**阻塞整个 OS 线程**，第一个协程永远回不来 → 死锁。

Raft 目前没踩到，因为两个 ticker 都把 `usleep` 放在锁外，
`leaderSendSnapShot` 也显式解锁后才做 RPC。**但这个约定没有被任何机制强制。**

### 6.3 两种"等待-唤醒"机制

| 机制 | 用在 | 实现 |
|---|---|---|
| `applyChan` | Raft → KvServer（单消费者） | `LockQueue<ApplyMsg>`，独立线程 `Pop()` 阻塞 |
| `waitApplyCh[index]` | apply 线程 → RPC 线程（按 index 会合） | `map<index, LockQueue<Op>*>`，`timeOutPop` 带超时 |

`LockQueue` 是"Go channel 的 C++ 模拟"（`util.h:61` 的注释），
`Push` 用 `lock_guard` + `notify_one`，`Pop`/`timeOutPop` 用 `unique_lock` + `wait`。

## 7. 时序参数

全部集中在 `src/common/include/config.h`：

```cpp
const bool Debug = true;
const int  debugMul = 1;                              // 慢网络下整体放大

const int HeartBeatTimeout = 25 * debugMul;           // ms
const int ApplyInterval    = 10 * debugMul;           // ms
const int minRandomizedElectionTime = 300 * debugMul; // ms
const int maxRandomizedElectionTime = 500 * debugMul; // ms
const int CONSENSUS_TIMEOUT = 500 * debugMul;         // ms，KvServer 等 apply 的超时

const int  FIBER_THREAD_NUM = 1;
const bool FIBER_USE_CALLER_THREAD = false;
```

**两个值得注意的关系**：

- `HeartBeatTimeout` 比选举超时小 12–20 倍 ✅ 符合 Raft 要求
- **`CONSENSUS_TIMEOUT == maxRandomizedElectionTime == 500ms`**
  → 只要发生一次最长选举，客户端的请求就必然超时并重试。不算错，但把
  `CONSENSUS_TIMEOUT` 设成选举上限的 2–3 倍会更稳。

**`Debug = true` 的代价**：`DprintfKVDB` 每 apply 一条命令就 `display_list()`
打印整个跳表（O(n)），且不受任何运行时开关控制。

## 8. 序列化：三个层次

这个项目的序列化是**嵌套的**，读代码时容易迷路：

```
┌─ protobuf ─────────────────────────────────────────┐
│  PutAppendArgs { Key, Value, Op, ClientId, ReqId }  │   ← RPC 参数
│  LogEntry { Command: bytes, LogTerm, LogIndex }     │   ← 日志条目
└─────────────────────────────────────────────────────┘
                    └─ Command 里面是 ↓
┌─ boost text archive ───────────────────────────────┐
│  Op { Operation, Key, Value, ClientId, RequestId }  │
└─────────────────────────────────────────────────────┘

　快照更夸张（两层 boost 嵌套）：
┌─ boost text archive（外层，KvServer::getSnapshotData）┐
│  { m_serializedKVData: string,  m_lastRequestId }     │
│     └─ 里面又是一份 ↓                                  │
│  ┌─ boost text archive（内层，SkipList::dump_file）─┐ │
│  │  SkipListDump { keyDumpVt_, valDumpVt_ }        │ │
│  └──────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

**为什么 `Op` 用 boost 而不用 protobuf？** 因为 `LogEntry.Command` 是 `bytes`/`string`，
要让 `Op` 直接用 protobuf 就得在 `LogEntry` 里嵌套一个 `Op` 消息类型——
而 `Raft` 希望"日志内容是不透明的字符串"。用 boost 文本归档是绕开这个的办法。

代价是**体积膨胀**（文本归档逐字符转义）和**嵌套解析**。

## 9. 实测性能

环境：3 节点（同一台机器，`fork` 出来）+ 客户端，`taskset` 绑核 0-3，**未做任何配置优化**。

### 吞吐与延迟

| 客户端线程 | 吞吐 | P50 | P99 |
|---:|---:|---:|---:|
| 1 | 41 ops/s | 20.5ms | 31.5ms |
| 2 | 83 ops/s | 20.6ms | 31.7ms |
| 4 | 166 ops/s | 20.6ms | 32.5ms |
| 8 | **166 ops/s**（饱和） | 50.3ms | 81.2ms |

**故障注入**（压测中 `kill -9` 一个 follower）：max 延迟 **403ms**，自动恢复，**0 丢数据**。

### 延迟拆解：85% 是空等

| 来源 | 平均 | 依据 |
|---|---:|---|
| 等下一次心跳 | **12.5ms** | `Raft::Start` 不触发复制，均匀等待 `HeartBeatTimeout/2` |
| 等 `applierTicker` 轮询 | **5ms** | `ApplyInterval=10ms` |
| RPC 往返（loopback） | ~0.5ms | |
| 实际计算 | **<1ms** | |
| **合计** | **≈18ms** | 实测 20.5ms |

**结论：这个系统 85% 以上的延迟花在轮询等待上，不是计算。**
`raft.cpp:969` 的注释承认了这一点，并且注明作者试过"收到命令立刻发"但失败了。

### 吞吐不随数据量退化（反直觉）

| 单轮操作数 | 吞吐 | P50 |
|---:|---:|---:|
| 500 | 42 ops/s | 20.43ms |
| 1500 | 42 ops/s | 20.59ms |
| 3000 | 41 ops/s | 20.75ms |

理论上"每命令一次全量快照"是 O(n²)，但**实测到 n=3000 都没退化**——
因为常数极小（n=3000 时快照才 64KB），而 20ms 的等待是常数。
**这个 O(n²) 要到十万量级才会成为主导。**

### 与真实系统对比

| | 单客户端写延迟 | 吞吐 |
|---|---|---|
| 本项目 | ~20ms | 166 ops/s（4 核饱和） |
| etcd（同为 Raft） | ~1–2ms | 10k–50k ops/s |

差 10–25 倍（延迟）、50–300 倍（吞吐）。**差距不来自 Raft 算法，而来自三个实现选择**：

1. `Raft::Start` 不触发复制（-12.5ms/op）
2. `applierTicker` 每 10ms 轮询（-5ms/op）
3. 每 peer 每心跳一个 `std::thread`（约 80 次线程创建/秒）

**前两条修掉，单客户端延迟可从 20ms 降到 ~2ms，吞吐提升约 10 倍**——不需要动 Raft 的任何算法逻辑。

## 10. 设计决策与取舍

这部分是**读这个项目真正该带走的东西**——不是代码怎么写的，而是为什么这么写。

### ✅ 做得好的

| 决策 | 价值 |
|---|---|
| **共识层与状态机靠 `string` 解耦** | `Raft` 不知道 `Op` 是什么，状态机可替换（CLAUDE.md 明确说"理论上可替换为任意 KV 存储"） |
| **`(clientId, requestId)` 去重** | 客户端"至少一次"投递 + 服务端去重 = "恰好一次"效果，是 Raft 客户端语义的标准做法 |
| **`waitApplyCh` 按 index 会合** | RPC 线程不必轮询，`timeOutPop` 带上限，避免永久阻塞 |
| **快照格式由服务层定义** | `Raft` 只搬运字节流，不解析——保持了分层 |
| **`Raft` 继承生成的 protobuf Service** | 同一个对象既提供 RPC 服务又持有全部状态，省掉一层转发（代价见下） |
| **`DEFER` 替代 Go 的 `defer`** | 用 RAII 管理锁和清理，`persist()` / `unlock()` 写在入口处，可读性好 |

### ⚠️ 有争议的

| 决策 | 问题 |
|---|---|
| **日志转义用 boost 而非 protobuf 嵌套** | 体积膨胀、双层解析，但保住了"对 Raft 不透明" |
| **`AppendEntries1` 逐条比对而非截断** | 为了容忍 RPC 乱序，但显著复杂化，且引入了 `myAssert` → `exit` 的崩溃路径 |
| **引入 `fiber` 协程库** | 2499 行只用来把 2 个定时器放进 1 个线程；而真正该用协程的地方（每心跳每 peer 起线程）没用 |
| **`Raft` 继承 Service** | 服务端实现和 RPC 入口耦合在一个类，`AppendEntries` / `AppendEntries1` 这种命名就是这么来的 |
| **启动靠固定 `sleep`** | `sleep(6)` + `sleep(nodeCount - me)`，时序脆弱 |
| **`CONSENSUS_TIMEOUT` 等于选举超时上限** | 每次换届必然产生一批客户端超时重试 |

### 🔴 应该避免的（本项目实际踩了）

| 反面教材 | 教训 |
|---|---|
| **`Persister` 构造时 `trunc` 清空落盘文件** | "实现了"≠"生效了"——整套持久化代码一行不缺，但从未生效 |
| **`Uuid()` 用 `rand()` 却不 `srand()`** | 跨模块的契约缺陷：单看 `Uuid()` 或单看 `ifRequestDuplicate()` 都正常 |
| **`send(fd, ..., 0)` 不处理 SIGPIPE** | 库不该让调用方因为"对端挂了"就死掉 |
| **`myAssert` 直接 `std::exit`** | 断言失败应该可捕获/可降级，不该静默终止整个节点 |
| **用 `shared_ptr<int>` 跨线程计票** | `shared_ptr` 只保证引用计数安全，不保证它指向的 `int` |
| **`m_configMap.insert()` 导致重复 key 静默取首值** | 静默取错值比报错更糟 |
| **大量无条件 `std::cout` 绕过 `Debug` 开关** | 全局开关必须真的全局 |

## 11. 缺陷索引

压测过程中发现并**已修复**的主要缺陷（完整清单与实测证据见
[benchmark/README.md §8.5](../benchmark/README.md#85-压测中发现并已修复的缺陷)）：

| 严重度 | 缺陷 | 状态 |
|---|---|---|
| 🔴 | 跨进程 `clientId` 碰撞 → **静默丢写且返回 OK** | ✅ 已修复 + 已复现验证 |
| 🔴 | `Persister` 构造时清空落盘文件 → **崩溃恢复从未生效** | ✅ 已修复 + 探针验证 |
| 🔴 | `AppendEntries1` 缺 `return` → **节点进程 `exit`** | ✅ 已修复 |
| 🔴 | `send(...,0)` 未处理 SIGPIPE → **对端一挂本端被打死** | ✅ 已修复 + 故障注入验证 |
| 🔴 | `skipList::load_file` 把 key 当 value → 快照恢复后**数据损坏** | ✅ 已修复 |
| 🟡 | `now()` 用非单调时钟 → NTP 校时破坏选举定时 | ✅ 已修复 |
| 🟡 | `Op::RequestId` 未初始化 | ✅ 已修复 |
| 🟡 | `Persister` 写入不 `flush` | ✅ 已修复 |
| 🟡 | `MprpcConfig` 重复 key 静默取首值 | ✅ 已修复 |

**仍未修复的**（需要设计级改动，留给后续）：

| 缺陷 | 为什么没修 |
|---|---|
| `CondInstallSnapshot` 恒返回 `true` | 2D 的协商机制被架空，修它要重做整个 InstallSnapshot 流程 |
| `votedNum` / `appendNums` 无锁自增 | 需要改成 atomic 或重新设计计票 |
| `RpcProvider::Run` 里 `setThreadNum(4)` 硬编码 | 属调优参数 |
| `DPrintf` 的 `%s` 配 `&std::string`（8 处） | 机械改动，碰多个文件 |
| `Raft::Start` 不触发复制 | **性能最大的一处**，但作者尝试过并失败（原因未知） |

详细分析见各模块文档的「已知疑点」章节。

                      然后 kill -9 一个节点，看重新选主

                     Start → applierTicker → doElection → AppendEntries1
                     ⚠️ 不要从第 1 行顺序读，它是事件驱动的
